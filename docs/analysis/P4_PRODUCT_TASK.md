# P4｜产品视角：为什么用户永远等不到「有规律」

> 角色：P4 产品/用户体验专家　｜　日期：2026-10-18
> 数据口径：本机真实 3515 期（2003001–2026118），快照 `data/patterns_runtime.json`（v7-2，生成于 2026-10-18 15:42:50）
> 性质：**只读分析 + 规格**。本文不改任何代码/前端/数据，全部建议以「可贴进 UI 的文案」和「接口规格」形式给出。
> 诚实边界：本文任何一条建议**都不承诺提高中奖率**。EV 不随选号改变（`ev_ratio_full ≈ 0.45675`、`ev_ratio_sixth = 0.15625`）。

---

## 0. 先把用户的问题翻译成产品问题

用户反复问的是同一句话：「为什么一个有用的规律都找不到」。

这句话里其实叠了三个不同的抱怨，产品必须把它们分开回答，否则每一轮改进都会打在错的那个上：

| 用户真正在抱怨的 | 产品层面的性质 | 能不能靠"继续找规律"解决 |
|---|---|---|
| 「我花了钱，结果页告诉我什么都没有」 | **过程可信感缺失**：花钱前后的画面不完整 | ❌ 找规律解决不了 |
| 「你连一个说法都给不出，是不是系统不行」 | **没有验收台账**：系统没有"做成了什么"的成绩单 | ❌ 找规律解决不了 |
| 「是不是你标准太严？换个标准不就有了」 | **对"规律"这个词的误解**（这一条用户有一半是对的） | ⚠️ 只能靠"改定义 + 可自证"解决，不能靠放宽 p 值 |

**结论先行**：这不是"算法不够先进"的问题，也不是"用户不懂数学"的问题。这是一个**产品目标错位 + 词汇债**的问题：
产品把「找到统计显著规律」当作主目标 —— 该目标在数学上不可达（数据与均匀随机不可区分）；同时又在新功能上不断**扩大「规律」这个词的用法**，导致同屏出现 5 种判据不同、结论互相打脸的含义。
用户等的是一句统一的「有规律了」，而系统内部**根本不存在一个能让这 5 种含义同时说"是"的时刻**。

## 1. 用户的真实诉求 vs 产品实际覆盖（(a)–(e) 逐条判定）

用户口头上要的是"规律"，但拆开后真正想要的通常是下面 5 件事。判定依据全部是页面/接口/文案证据。

| # | 真实诉求 | 现有覆盖 | 证据 | 缺口（这是产品该补的） |
|---|---|---|---|---|

| **(e)** | **让"为什么没有规律"变成他自己能验证的解释** | 🔴 **基本没有** | 现有全部是"告诉用户结论"：`web/static/app.js:3134`（"这是实战裁决的正常结果，不是失败"）、`web/static/app.js:486`（"'无可用规律'是诚实的结论"）、`web/static/app.js:3491`（"准确率上不去不是调参问题"）。唯一带随机对照的是**内部研究文档** `docs/reviews/PHASE_USABLE_STUDY.md`（200 个随机窗口对照，15% 同向性），**用户看不到、也不能自己点** | ⚠️ 这是本轮最有价值的缺口。项目从 V4 起就有「随机性自证」传统（`docs/V10_IMPROVEMENT_PLAN.md:1279-1285`：注入偏置必须检出、纯随机不得误报），但这个传统**只存在于测试里，没有产品化给用户**。→ 见 §4（可自证实验） |

**一句话判定**：现有产品在 (b)(c) 上其实已经做出了真正值钱的东西，(a)(d) 只做了一半，(e) 完全没做。
而首屏把 (a)(b)(c) 的成绩全部让位给了一张写着「0」的规律卡。**用户不是没得到价值，是产品没有把价值放在用户看得见的地方。**

## 2. 定义债务：「规律」在产品里同时有 5 种含义

同屏共存、判据不同、结论互相打脸。**"有规律"在这个产品里没有唯一判据，所以用户永远等不到它。**

### 2.2 为什么会"永远等不到"

把 5 个判据列在一起，就能看出用户等的那个时刻在系统里**不存在**：

```
用户心里的一句话：「系统说有规律了吗？」
①  统计显著          → 0 条（数据与均匀随机不可区分，p_adj 最优 1.0）
②  形态恒等          → "可用"（5 条，但恒成立，与数据无关）
③  阶段有效          → 0 条（假设已被 4 组检验否证，usable_phase 默认关闭）
④  生命周期          → 未纳管（0 条进入状态机）
⑤  LLM 洞察          → 0 条，且代码层永久排除 → 不可能变成可用
```

- ①③④⑤ 恒为 0 或空，② 恒为真。**没有任何一次状态迁移能让用户看到「有规律」变绿。**
- 更麻烦的是用户能从 ② 看到"可用规律 5 条"，从 ① 看到"可用规律 0 条"，从 ⑤ 看到"AI 跑了三轮什么都没找到"。**三个数字互相矛盾，用户无法判断该信哪个。**
- 于是每一轮反馈都会回到同一句话（"规律太少 / 找不到 / 不准"），而每一轮修复都只能在同一组数字上换措辞。**这就是 V4→V11 的循环机制，不是开发者的疏忽。**

### 2.3 两条术语线索：「定义太狭隘」这个判断的正面价值

`lottery/api_app.py:197-207` 的注释是**全项目最诚实的一段话**，也是本轮唯一已经发生的"定义扩张"：

> 「此前要求 counts.usable > 0（显著规律），但 3515 期实测 0 条显著，会让严格模式永远哑火。V12 起改用**组合恒等约束**…作为"可用规律"」

**这个方向是对的**（承认主目标不可达 → 改用可达目标），**但实现方式是错的**：它没有改名，而是把新东西塞进了旧词里。
结果是「规律」这个词同时背了两个不相容的义务，用户看到的矛盾比修之前更大。

## 3. 「有用」的重新定义：8 个可判定产品目标

**总原则**：一个目标只要"可判定"，就必须满足三条 —— ① 答案唯一（代码能给对错）；② 不依赖"下一期开奖"；③ 不需要统计功效（30 行样本就能判）。

## 4. 用户可自证实验：「为什么找不到规律」的现场验证

> 这是本轮**最有价值**的交付。目标不是说服用户"数学上不可能"，而是让用户**自己**看到：同一台机器，喂给它**已知纯随机**的数据，也会输出同样的"找不到规律"。
> 若结论只出现在真数据上 → 结论有信息；若随机数据也一样 → 结论是机器的口径，不是数据的发现。

### 4.1 用户看到的三步（页面交互流程）

**入口**：全新页面「验证」标签（或「评估报告」顶部一张卡），首屏可见，标题带问号而不是感叹号。

```
┌──────────────────────────────────────────────────────────┐
│ 🧪 验证「找不到规律」是不是系统的锅            [开始验证] │
│                                                          │
│  这台机器对真实 3515 期开奖的结论是「没有可用规律」。      │
│  下面这个实验会另外生成 3515 期**已知纯随机**的假开奖，   │
│  再用完全相同的代码跑一遍。                              │
│  · 如果假开奖也得出现在同样的结论 → 结论来自检验口径；    │
│  · 如果假开奖里检出了显著 → 说明这套代码会误报，请告诉我们 │
│                                                          │
│  约 20~40 秒，只读，不会写入任何数据。                    │
└──────────────────────────────────────────────────────────┘
```

点击后（进度条 4 步，预计 20~40s；后端是纯计算，`asyncio.to_thread` 不阻塞）：

```
步骤 1/4  生成 3515 期假开奖（种子 42，可复现）        ✅
步骤 2/4  维度扫描：真实 vs 假 的 p 值分布            ✅  真实最优 p=1.0000 · 假 最优 p=0.9873
步骤 3/4  形态恒等约束：真实 vs 假                     ✅  真实 5/5 在带内 · 假 5/5 在带内
步骤 4/4  同一期号、同种子跑两次，比对结果是否逐位一致  ✅  一致
```

结果面板（**这是重点**：用"对照组"而不是"结论句"来表达）：

```
┌─────────────────────────────────────────────────────────────┐
│           真实开奖（3515 期）      假开奖（3515 期，纯随机） │
│ 维度扫描       94 组               94 组                     │
│ 预期假阳性     4.7 个              4.7 个                    │
│ 最优校正 p     1.0000              0.98xx                   │
│ 结论          「无任何维度显著」    「无任何维度显著」       │
│ 形态约束      5/5 在带内           5/5 在带内                │
│ 可复现        两次一致             两次一致                 │
├─────────────────────────────────────────────────────────────┤
│ 读数：真实数据与假数据的结论**完全相同**。                     │
│ 这说明「找不到规律」是这台机器面对随机数据时的正常输出，        │
│ 不是它没努力；反过来，它也没有在随机数据里凭空"造"出规律。      │
│ 注：假开奖的种子与期号已显示 —— 你可以用同样的种子自己再跑一次。│
└─────────────────────────────────────────────────────────────┘
```

**交互细节（必须实现，否则实验会变成"又一个结论"）**：

1. **可换种子**：「换一组假开奖再试（种子 43）」按钮。用户连点 3 次，看到三列假数据的结论都一样 —— 自证在这里完成。
2. **可换样本量**：下拉「1000 / 2000 / 3515 期」。1000 期时会看到"最优 p 更接近 0.05 附近波动"——这是真实的功效效应，**要如实显示**，不要藏。
3. **可复现校验**：页面显示 `seed` + 两次运行的结论哈希（如 `p_adj` 保留 6 位），并给一个「复制复现命令」按钮。
4. **诚实提示常驻**：实验**不生成任何号码**、**不写库**、**不改任何已有结论**；页面角标 `readonly=true`。
5. **失败也算通过**：若假数据里真的检出了显著维度（假阳性），面板必须写「本次检出 X 个显著维度 —— 在 α=0.05、m=94 下预期约 4.7 个假阳性，属正常范围」而不是红字报错。

### 5.1 前置条件：若 V12 采用「L1/L2/L3 三层」重新定义规律

> 说明：`L1/L2/L3` 截至本文成稿时**仓库内无成文定义**（`grep -rn "L1\|L2\|L3" docs/analysis/ lottery/ web/static/app.js` 零命中），以下按「**按证据类型分层、每层有独立名称与独立判据**」这一最可能形态判定。
> 若实际含义是「按**状态**分层」（如 强/弱/休眠）而非按**证据类型**分层，则仅 S-10 的判定需改写（见下），其余不变。

| 停止项 | 三层定义下是否自动失效 | 理由 |
|---|---|---|
| **S-1**（形态约束被叫「可用规律」） | ✅ **自动失效** | 分层的核心动作就是给每层独立名字；若形态约束被定为 L1 并更名，本条即已完成 |
| **S-2**（首屏头号指标「可用规律 0」） | ✅ **自动失效**（**但有一个致命前提**） | 只要不再存在「可用规律」这个单一总数，本条前提就消失。**前提：三层不得再求和**——见下方警告 |
| **S-4**（LLM 工坊叙事） | 🟡 **部分失效** | 若 V12 在定义层就把 LLM 定为"复核"而非"发现"，改名被吸收；但「AI 的正确输出可以是"没有发现"」这句定位仍需在 UI 明说，否则用户仍会读成"AI 没找到" |
| **S-6**（5 处互斥空态文案） | 🟡 **不减反增** | 单一口径消失后，空态从 1 种变成最多 3 种（三层各一个）。**若不强制统一组件，矛盾数量会翻倍**——本条优先级应**上调** |
| **S-11**（README 主句） | 🟡 **部分失效** | 若 V12 批次本身包含 README 重写则被吸收；否则仍须改 |
| **S-3**（闭环按钮常亮 / `source=="llm"` 永久排除） | ❌ **不失效** | 成因是代码级永久排除（`lottery/patterns_runtime.py:125-131`）+ 单次 1~8 分钟成本，与"有没有头号数字"无关 |
| **S-5**（规律时效横幅 / 阶段假设） | ❌ **不失效** | 问题是"阶段假设已被 4 组检验否证却仍在讲"，分层不解决 |
| **S-7**（搜索空间 = 94 组） | ❌ **不失效** | 属多重检验代价叙事，与分层正交 |
| **S-8**（`only_interesting` 默认 true） | ❌ **不失效** | 属多尺度卡口径不一致，与分层正交 |
| **S-9**（9 段 vs 23 段） | ❌ **不失效** | 属阶段切分口径漂移，与分层正交 |
| **S-10**（生命周期"流动"叙事） | ⚠️ **取决于 L1/L2/L3 的性质** | 若三层是**状态分层**（强/弱/休眠）→ 与 `rule_lifecycle` 同构，本条被**吸收，自动失效**；若三层是**证据类型分层**（恒等约束/统计证据/前向验证）→ `lifecycle` 仍是独立空转档位，本条**不失效** |

**小结**：自动失效 **2 条**（S-1、S-2），部分失效 **3 条**（S-4、S-6、S-11），不失效 **5 条**（S-3、S-5、S-7、S-8、S-9），条件性 **1 条**（S-10）。

> ⚠️ **必须提前写死的两条约束（否则分层会重蹈覆辙）**
>
> 1. **禁止求和。** 现有代码已有反面先例：`lottery/patterns_runtime.py:203-205` 的 `counts.usable = _n_long + _n_phase`（注释写"与旧口径兼容"）。若 V12 也给出「可用规律 = L1+L2+L3」的总数，首屏就会出现 **5 条"可用"而其中 0 条有预测力** —— 比现在的「0 条」更误导。三层的数字必须**分开陈列、不提供合计**。
> 2. **三层名称里禁止出现「可用」。** 「可用」是本次定义债务的**债主**：它同时意味着"能被使用"（L1 恒等约束，真）与"有预测价值"（①，假）。分层若保留这个词（如"可用·恒等层 / 可用·统计层"），债务原样保留、且更难察觉。建议改用**证据类型**命名：`恒等约束` / `统计证据` / `前向验证`。

## 6. 对用户问题的直接回答（可直接贴进 UI，240 字）

> **为什么一个规律都找不到？**
>
> 因为这个系统的检验标准是"能不能预测下一期"，而双色球每期开奖是独立的。我们拿 3515 期真实数据做了 94 组维度的扫描：最显著的 p 值经校正后是 1.00，而纯随机数据本来就该出现约 4.7 组"看起来显著"。**找不到，是因为数据里没有，不是流程没跑。**
>
> 你说"规律定义太狭隘"—— 这句话有一半是对的：之前我们把"规律"只理解成"能预测下一期的统计显著模式"，这个目标数学上无法达成，我们却一直拿它当主要目标，于是你每次都只看到"0"。**这一半我们接受，并且已经改了**：现在真正在工作的三件事是 —— ①每注号码的形态落在真实开奖常见区间内（可验证，恒成立）；②固定预算下把奖级概率、方差、覆盖算清楚（可算，精确枚举）；③让你自己点一下，看到随机数据也会得到同样结论。
>
> 但另一半要说明白：**"换一个更宽的定义"不等于找到了规律。** 放宽标准只会让噪声变成"发现"。所以我们的答案不是"再找找"，而是把"有用"改成三件能判定的事。
>
> 这三件事**都不会提高中奖率** —— 每 ¥2 的长期期望回报约 ¥0.91，这一点不会因为任何设置改变。

## 7. 风险：继续以「找规律」为主目标，接下来会重复发生什么

### 7.1 已经发生的循环（6 次，可逐条核对）

| 轮次 | 版本 | 当时的目标措辞 | 实际交付 | 用户的下一句 |
|---|---|---|---|---|
| 1 | V4 诚实口径重构 | 覆盖率优化 + 严格样本外 | 揭示 EV 不变、覆盖改分布不改期望 | "规律还不够多" |
| 2 | V5 自进化 | 战斗回放 + LLM 提炼 + A/B 裁决 | **0 validated / 0 rejected / 9 unchanged**（`README.md:155`） | "近期规律都不生效" |
| 3 | V6 阶段有效性 | 阶段时效 + 多维度发现 + LLM 工坊 | 建成状态机；0 条 persistent / 0 条 emerging | "规律不太多、AI 参与度低" |
| 4 | V7 AI 规律闭环 | 挖掘→验证→注册→出号 | 快照 `usable=0 / monitor=1`；LLM 三轮后自推翻，0 条（`README.md:54-57`） | "仍然显示无显著规律" |
| 5 | V8 阶段切分 | 9 段 → 自适应 23 段、改检验口径 | 检出力翻倍（0.31→0.65），结论**不变**：0 条（`README.md:29-31`） | "还是找不到" |
| 6 | V11/V12 严格模式 + 形态约束 | 让严格模式不哑火 | 用**组合恒等式**顶替显著规律（`lottery/api_app.py:197-207`） | "为什么一个规律都找不到"（本轮） |

> 关键观察：**第 5 轮的结论最早由项目自己写下了** —— `README.md:31`：「**改切法确实把检出力提高了一倍，但数据里确实没有可用规律 —— 这是结论，不是失败。**」
> 而第 6 轮仍然在同一目标上换了方法（V12 换定义）。**循环没有被打破，只是换了形式。**

### 7.2 如果不改，接下来 6 条会按顺序发生

1. **用户会继续用同一句话反馈**（"规律太少 / 找不到 / 不准"），因为系统里没有任何一处能让 5 种口径同时变"有"（§2.2）。
2. **团队会继续在两个错误选项间摆动**：要么放宽标准（改 p 阈值 / 加维度 / 换阶段切法），要么扩大定义（把别的恒等式也叫"规律"）。二者**都会在下一轮产生新的术语冲突**，而不是产生价值。
3. **第 7 次"扩大定义"几乎必然发生**，且会更难解释（形态约束已经是"恒等式"这一极端；下一个只能是"经验区间"，比现在更难证伪）。
4. **已经做出来的真资产会被继续埋着**：票单分布（G2/G3）与形态约束（G1）在"更多"里，而首屏的头号数字永远是 0。**用户每看一次首屏，就多一次"这系统没用"的判断。**
5. **成本会继续泄漏**：首屏常亮的「AI 规律闭环」按钮（`web/static/app.js:490-492`）每被点一次就消耗 1~8 分钟的 LLM 三轮调用，而结构上不可能产出可用规律（`patterns_runtime.py:125-131`）。用户的期待被转化为账单。
6. **信任会反转**：用户看到「可用规律 0」与「可用规律 5 条」同屏（①②），最可能的结论是"系统自己都没搞明白"，而不是"数据里没有"。**这比"没有规律"更糟** —— 它会否掉系统已经做对的部分（G1–G4）。

### 7.3 打破循环的唯一判据（可验收）

把产品主目标从"找到规律"换成上述 8 个目标后，**每一轮迭代都必须能回答一个问题**：

> **"这一版改进了 G1–G8 里的哪一项？给出改前/改后的两个数。"**

- 答不出来 → 这一版不应该发。
- 若答案为"找到了规律" → 请先回到 §2.2，确认你用的是 5 种定义里的哪一种，以及其余 4 种是否会显示矛盾。
