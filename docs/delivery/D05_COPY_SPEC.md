## 〇、开工前必须先说的一件事：齐交付给的四个数字里，有一组口径混用

我按 `blue_coverage.optimize()` 实测复算了你给的蓝球事实，**三组完全吻合，一组不能同屏**：

| 你给的事实 | 我的复算 | 判定 |
|---|---|---|
| 蓝球铺满 ⇒ P(≥1 中) = 100% | `n=16 → p_cover = 1.000000` | ✅ |
| 成本 ×16：16 注 = 32 元 | `cost = 32.0` | ✅ |
| 回报率恒 15.6%（六等奖）/ 52.3%（全奖级），与注数无关 | `ev_ratio_sixth = 0.156250`（n=5/10/16 全等） | ✅ |
| 概率杠杆 ×3.853（0.085473 → 0.329347） | `0.329347 / 0.085473 = 3.853` | ✅ 数值对 |
| **期望回收 16.73 元** | `32 × 0.5228 = 16.73` → 这是**全奖级**口径；同金额的**六等奖**口径只有 `32 × 0.15625 = 5.00` | ⚠️ **不能和 15.6% 同屏** |

**问题**：16.73 元是「整注（一~六等全计，含一/二等奖按 684 万假设）」的期望回收；
而 15.6% 是「仅六等奖」的返奖比。**若页面上并列出现「期望回收 16.73 元」与「回报率 15.6%」，
用户做除法会得到 52.3%，与旁边 15.6% 冲突 —— 这不是造假，但会被认定成造假。**

**处置**：本规格 §二 规定两种口径必须**成对出现、不许交叉**
（六等奖：5.00 元 ↔ 15.625%；全奖级：16.73 元 ↔ 52.29%（strict），且必须带奖金假设）。

### 〇-B 口径矩阵（全部实算，勿凭记忆引用）

`_single_ticket_ev(assumption, sixth=...)` 两个开关组合出四个数，**必须始终标明是哪一个**：

| 奖金假设 | `sixth` | `ev_ratio` | 渲染成 | 谁在用 |
|---|---|---|---|---|
| `first=5,000,000` / `second=150,000`（即 `PRIZE_ASSUMPTION_TABLE_A` 当前值） | `published` | 0.456732 | 45.67% | `engine.py` docstring 的 `ev_ratio_full ≈ 0.45673` |
| `first=5,000,000` / `second=150,000`（同上） | `strict` | 0.447714 | **44.77%** | 无（原「500万→47.1%」是错的，实测 44.77%） |
| 684万 / 20.5万 | `published` | 0.531925 | **53.19%** | ⚠️ **`routes_portfolio.py` 当前用它** |
| 684万 / 20.5万 | `strict` | 0.522907 | **52.29%** | Lead 红线、`popularity.py:263` 用户可见文案 |

`published` 与 `strict` 的差别（`engine.py:1767-1773`）：`published` 的六等奖取蓝球**边际**概率
`pb=0.0625`，与高奖级**重复计数**；`strict` 取互斥集合 `(p_r(0)+p_r(1)+p_r(2))·pb`。
**`strict` 是语义正确的那个，`published` 会系统性偏高约 0.9pp。**

> **口径引用规则（齐交付 2026-10-21 追加）**：引用 EV 必须同时写死三样 ——
> **`first`/`second` 的字面值 + `sixth` 取值 + 计算函数**。
> 不许只写常量名（如「表 A」）：常量表会变，名字不变，等于把口径外包给一个会漂移的东西。
> 也不许只写「52.3%」——那个数在四个组合里只对其中一个成立。

**D2 的修法：四项全部 `.3f`（齐交付 2026-10-21 驳回我的混排方案，实测成立）**

我初版建议「176 与 178/186 改 `.3f`，177（净亏）保持 `.2f`」—— **该建议作废**。
齐交付用算术闭合检验驳回，我复算确认：

```
cost=20.0  ev=3.125  net=16.875
方案 A（全 .2f）   ：期望 3.12   净亏 16.88   用户反算 20−3.12  = 16.88    ✅ 闭合
方案 B（我的混排） ：期望 3.125  净亏 16.88   用户反算 20−3.125 = 16.875   ❌ 差 0.005
方案 C（全 .3f）   ：期望 3.125  净亏 16.875  用户反算 20−3.125 = 16.875   ✅ 闭合
```

**关键：`净亏 = cost − ev` 是恒等式，三项必须同精度。**

**更正后的改法**：`blue_coverage.py:176/177/178/186` **四项全改 `.3f`** → `3.125 元 / 16.875 元 / 15.625%`。

→ 净亏的建议呈现：`净亏 16.875 元`，或直接写 `亏损 16.875 元` 以免和 `16.88` 的记忆冲突。

### 〇-D 「渲染面」的操作定义（写死，避免各人各扫一半）

「渲染面」这个词太抽象，落地时容易只想到「HTML + JS」。**操作定义如下，四层缺一即漏**：

```
渲染面 =
  ① HTML 文本节点（含 index.html 的可见文本）
+ ② JS 字符串字面量（含相邻拼接归一化：`"a" + "b"`）
+ ③ CSS content: 属性（会把文字直接画到页面上）
+ ④ 模板 / innerHTML / textContent 拼接后的结果
```

**这不是理论清单**：我漏了 ③，导致 `style.css:637` 未被计入（严QA 补上）；
若漏 ④，动态拼出的禁用词永远抓不到。
**已知不覆盖**：`String.fromCharCode` / `\uXXXX` 转义 / 变量拼接 —— 必须写进测试注释作为边界，不许假装全守。

### 〇-E 同屏一致性四对必查（齐交付验收清单同步）

| 对 | 两个值 | 来源 |
|---|---|---|
| 1 | `52.29%` vs `53.19%` | `ev_ratio_full` |

## 一、大众偏好度页面

### 1.1 标题与一句话副标题

**标题（可抄）**
```
👥 大众偏好度
```

**副标题（可抄，必须一行，必须紧跟标题，不许截断/收起）**
```
这注号码历史上会被多少人选——只给三档，不预测开奖，也不改变中奖概率。
```

**副标题的三处设计取舍（每条都对应一个可验收约束）**

1. **「多少人选」而不是「受欢迎度/热度」**：后两个词都暗示「值得选」。句子的主语必须是**选号的人**，不是号码。
2. **「只给三档」**：把输出形式写进副标题。用户看到「偏热门」时不会去找「具体几注」，因为副标题已说明只有三档。
3. **「不预测开奖，也不改变中奖概率」**：两件事分开写，因为它们是两件事 —— 前者是能力缺失，后者是**即使有能力也不改概率**。合成一句会让用户以为「只要不预测开奖就没事」。

**禁止**：`智能评估`、`热度分析`、`精准画像`、`帮你避开热门`、`提高中奖几率`、`选号建议`。

### 1.2 「能说」与「不能说」对照（各 3 句式，可直接抄）

**✅ 能说（可抄）**

| # | 句式 | 什么时候用 |
|---|---|---|
| S1 | `这注号码的形态，历史上属于偏冷门（三档中的最低一档）。` | 档位 = `low` |
| S2 | `这个档位只表示「有多少人可能选同样的号」，与开奖结果无关。` | 任何档位，紧接结论 |
| S3 | `同样中头奖时，热门形态分给的人更多——所以冷门形态能少分一点。` | 解释「这东西有什么用」时 |

**❌ 不能说（禁止出现）**

| # | 句式 | 为什么禁止 |
|---|---|---|
| N1 | `这注中奖概率较高 / 更值得选 / 成功率更好` | 直接违反 N2（EV 由恒等式钉死） |
| N2 | `预计本期约有 8 注会选这种形态` | 把排序输出伪装成定值。模型 R² 仅 0.5%，任何具体注数都是编的 |
| N3 | `避开热门可以多拿奖金` | 弹性实测 `−0.088`，收益区间 0.005~0.18 元/注。单说「多拿」是夸大 |

**为什么 N3 尤其要禁**：团队裁决记录过一次真实翻车 —— 曾算出「避开极端热门可让头奖金额高 46.5%」，
后被产品审查员用弹性检验推翻（`p1` 降 20%，金额只涨 1.99%）。那个 46.5% 是把奖池规模差异
误读成避开热门的收益。**这类数字一旦上线过一次，整份报告的可信度就没了。**

### 1.3 R²=0.5% 的人类可懂类比

不用「R²」，不用「解释力」，不用「方差」。**可抄**：

```
这个模型的靠谱程度，大致相当于：用一个人的身高去猜他的体重——
方向大体对（高的人通常重一些），但具体到某一个人，猜得经常不准。
```

**关于类比里数字的口径说明（写进测试注释，不用给用户看）**

- 你给的硬事实是 **R²≈0.5%**（置换 p=0.005，5 折 CV）；
- 我在代码里读到的是 `popularity.py` 模块 docstring 的 **增量 R² = +0.0077（0.77%）**，
  且注明「不同折数 3/5/8/10 下恒为 +0.0077」。两者**都是代码里真实存在的数**，只是标注方式不同
  （一个按「约 0.5%」口头，一个是 0.77% 实测）。
- **处置**：给用户的文案**不写百分比**（写了就必然要选一个数，而 0.5% 与 0.77% 会被拿来互相打脸）。
  文案只说方向（「大体对、具体不准」）。**百分比只出现在展开后的技术细节里，且必须带出处**
  （`R²=0.0077（5 折 CV）· 置换 p=0.005`）。

为什么这条值得单独规定：**同一个功能在两个地方给出 0.5% 和 0.77%，是本项目历史上
「一个 usable 两个意思」那类事故的同一个形状。** 用户不会去分辨哪个是 CV、哪个是增量，他只会说「你们自己都对不上」。

### 1.4 必须同屏出现的数字（consent 清单）

以下 **5 项必须在同一屏、同一张卡内**，缺任一项该卡不得渲染（不是折叠，是不显示）：

| # | 必须出现 | 出自 | 呈现要求 |
|---|---|---|---|
| C1 | 档位（偏冷门 / 常见 / 偏热门） | `describe()['tier_label']` | 主视觉，字号最大 |
| C2 | 该档位的诚实说明 `caveat` 全文 | `describe()['caveat']`（`popularity.py:119-127`） | 与档位同屏，不许折叠 |
| C3 | `中头奖概率恒为 1/17,721,088，不受选号影响` | `describe()['honesty']` | 与档位同屏 |
| C4 | 效应量（展开区）：`R²=0.0077（5 折 CV）· 置换 p=0.005` | `describe()['r2_increment']` | 可展开，但**默认展开** |

## 二、蓝球去重覆盖页面

### 2.1 首屏必须出现的披露句（可抄原文，五句，不许删减）

**以下为后端 `disclosure_lines` 在 n=10 时的实测输出（2026-10-21 实跑），前端必须逐字渲染：**

```
同样买 10 注：「至少中一次蓝球（¥5）」的概率从 47.55% 提升到 62.50%。
但成本是 20 元，六等奖期望回收 3.12 元，净亏 16.88 元。
六等奖返奖比恒为 15.62%，**与注数无关** —— 覆盖优化改变的是中奖分布，不是期望收益。
整注（一~六等全计）返奖比约 53.2%，**长期仍为负期望**。
中头奖概率恒为 1/17,721,088，**不受选号或覆盖策略影响**。
```

⚠️ **注意 3 处与「理想文案」的差异，都是待修缺陷（见 §〇-C）**：
- `3.12` / `15.62%` 应为 `3.125` / `15.625%`（`:.2f` 截断，D2）；
- `53.2%` 应为 `52.29%`（`published` vs `strict`，D1）。
修完 D1/D2 后本块应变为：`3.125 元` / `15.625%` / `52.3%`。
**在上述两条修好之前，前端仍应原样渲染 `disclosure_lines`（不要为了对齐而手写数字）** ——
手写会制造第三种版本。

**这五句与后端 `blue_coverage.py:128-140` 的 `disclosure_lines` 逐字一致** ——
前端应**直接渲染 `disclosure_lines` 全文**，不要在 JS 里重写一遍。
理由：重写必然产生漂移，而漂移的两个方向（漏一句 / 改数）都会构成误导。

**首屏层级要求**：这五句必须在**卡片内、结果数字之后、同一次滚动内**出现。
不许放进 tooltip、不许默认折叠、不许用 `text-overflow` 截断。

### 2.2 如何避免「更容易中大奖」误读 —— 具体文案手法（不是原则）

**手法 A：把「中蓝球」写成具体金额，不写奖级名**
- ✅ `至少中一次蓝球（¥5）`
- ❌ `至少中一次六等奖`、`至少中一次奖`
- 理由：`中奖` 两个字会向上兼容到「中大奖」；`¥5` 是硬上限，用户读到的第一秒就知道这是小钱。

**手法 B：概率句后面立刻跟金额句，中间不许插任何内容**
```
同样 10 注：…从 47.55% 提升到 62.50%。      ← 概率
但成本是 20 元，六等奖期望回收 3.13 元，净亏 16.88 元。   ← 金额，必须紧邻
```
- 理由：用户扫读时以「句」为单位。两句之间的任何插入（分隔线、图标、换行空行）
  都会让概率句独立成立。**「但」字必须是概率句的下一句第一个字。**

**手法 C：用「多久中一次」而不用「更容易中」**
- ✅ `平均每 1.6 注期能撞上一次 ¥5（10 注口径）`
- ❌ `更容易中奖`
- 理由：「多久一次」是频率陈述，可复算；「更容易」是概率方向暗示，会外溢到大奖。

**手法 D：明确写出天花板**
```
这套方法的天花板就是「每次一定有 ¥5 拿」——它碰不到一等奖。
```
- 理由：不写天花板，用户会自动推断「覆盖得越满越好」，进而推「那不是迟早中大奖吗」。
  这句必须出现，且用「碰不到」这种直白说法。

**手法 E：`honesty_flags` 三个是/否直接用中文标签渲染，不许改写成句子**
```
提高中奖概率：否    提高期望收益：否    提高中奖频率：是
```
- 理由：三个否/是并排，是唯一不会被修辞化解的形式。改写成句子（「虽然提高频率但……」）
  就给了「但是」的操作空间。

### 2.3 「×3.853 杠杆」与「32 元成本」的同屏方案

**先给结论：上下排列，成本在上，杠杆在下，且杠杆必须带「基于什么」的前提。**

```
┌─────────────────────────────────────────────┐
│  蓝球去重覆盖 · 16 注                        │
│                                             │
│  成本            32 元   （16 注 × ¥2）      │  ← 第 1 行：成本
│  六等奖期望回收    5.00 元                    │  ← 第 2 行：同期同口径回收
│  净亏            27.00 元                    │  ← 第 3 行：净结果
│  ─────────────────────────────────────────  │
│  覆盖效果：16 个不同蓝球 → 至少中一次 ¥5 的概率 │  ← 第 4 行：概率句
│           1/16（随机重复）→ 16/16（覆盖）     │
│  ─────────────────────────────────────────  │
│  披露（全文，不可拆开读）：                    │
│  …五句…                                      │
└─────────────────────────────────────────────┘
```

**三条理由（对应三个可验收约束）**

1. **成本必须在概率之前**。用户从上往下读，第一组数字是「要花多少」。若概率在前，
   用户已经形成「覆盖很有效」的印象，后面的成本会被当作附注。
   → 验收：成本行的 DOM 顺序必须先于概率行。
2. **×3.853 不许单独出现，必须带分子分母**。单写「×3.85」是营销数字；
   写出 `1/16 → 16/16` 用户能自己算，也能看出「这是覆盖率的比值，不是收益的比值」。
   → 验收：杠杆旁若没有分子分母，视为不合格。
3. **杠杆放在披露之上、成本之下**。放披露之下会被当成「补充说明」跳过；放成本之上会抢首行。
   → 验收：DOM 顺序 = 成本组 → 杠杆组 → 披露组。

**关于「16 注 / 32 元」时的特殊约束（与 10 注不同）**
- `n=16` 时 `P(≥1 中蓝) = 100%`。这是**恒等式**，但它极易被读成「必中」。
- **额外必须同屏**：`100% 指的是「至少中一次 ¥5」，不是「中奖」` + `期望回收 5.00 元，净亏 27.00 元`
  + `整注口径期望 16.73 元（含一/二等奖按 684 万假设），长期仍亏`。
  ← 但注意：16.73 必须与 **52.29%（strict 口径，684万/20.5万）** 成对出现，**不得**与 15.625% 同屏（见 §〇-B 口径矩阵）。

## 三、一句话判断：接入这两个端点，是让产品更诚实，还是更危险？

**答：默认是「更危险」，只有在满足下列三个硬约束时才转为「更诚实」。**

理由不是这两个端点的数据有问题 —— 数据是这两个端点**唯一没问题的地方**（全是组合恒等式与
可复算的样本外检验）。危险来自**呈现的单向性**：

1. **两个端点卖给用户的是「收益」，但它们的诚实内容全是「限制」**。
   用户打开蓝球覆盖卡，第一眼想看的是 62.50%（比 47.55% 大，直觉上就是「变好了」）。
   而真话是「净亏 16.88 元」。**人只看第一眼的收益，不看同屏的限制** —— 这不是推测，
   而是「同屏」这个词本身的前提：如果同屏就够，就不需要规定 DOM 顺序了。
2. **`×3.853` 是这套设计里最危险的一个数**。它是我在代码里见过的最容易被误读的字段：
   它是**概率的比值**（覆盖/重复），却长得像一个**收益倍数**。而且它越大（注数越多），
   亏得越多。**一个随亏损增加而变大的「增益」数字，是最坏的产品形状。**
3. **popularity 的「偏冷门」标签会被读成「冷门号」。** 用户对「冷门」的默认理解是
   「别人不买，中了我独吞」→ 这正好**暗示**了一种选号策略。而真相是：中奖概率完全不变，
   仅在真中头奖时少分一点，量级 0.005~0.18 元/注。

**因此，若以下三条不满足，我建议这两个卡先不要上线**（数据留着，入口先不给）：

| # | 硬约束 | 为什么不能让步 |
|---|---|---|
| H1 | 首屏 DOM 顺序固定：**成本 → 概率 → 杠杆 → 披露全文** | 顺序是唯一不依赖用户注意力的手段 |
| H2 | `×3.853` 与 `p_gain_ratio` **必须**与分子分母、与净亏同屏；不许出现在任何摘要/角标/分享卡片里 | 摘要是最容易被单独传播的形态 |
| H3 | popularity 卡**不得**出现「注数」，且 `caveat` + `1/17,721,088` 必须与档位同屏 | 档位脱离边界就等于选号建议 |

**满足这三条后的结论**：这两个卡会是**全系统唯一经得起追问的收益卡** ——
因为它们的收益是真的（概率上，可枚举验证），限制也是真的（恒等式上，可计算验证）。
**这正是「有益」的正确形状：不是把限制藏起来，而是把限制做成收益的同义词。**

你现有的验收标准「必须同屏披露成本」是**必要但不够**的。建议加两条：
- **顺序**（H1）：同屏不等于无序，先成本后概率；
- **不可扩散**（H2）：杠杆与比值字段不得进入任何摘要、角标、复制文本、分享卡片。
