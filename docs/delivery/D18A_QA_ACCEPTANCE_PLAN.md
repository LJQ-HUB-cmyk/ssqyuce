## §1 逐行分类：正断言 vs 负断言（**修法完全不同**）

| 行 | 断言 | 类型 |
|---|---|---|
| `v10_llm_arm:359` | `assert '!= "llm"' in src` | **正**：某表达式存在 |
| `v10_llm_arm:386` | `assert 'channels.get("llm_can_pick")' in src or "llm_can_pick" in src` | **正**（弱：有 `or` 兜底） |
| `v10_llm_arm:387` | `assert 'llm_can_pick' in src` | **正** |
| `v10_ticket_dist:382` | `assert "portfolio_expected_value" not in src` | **负**：标识符不得出现 |
| `v10_ticket_dist:383` | `assert "expected_reward" not in src` | **负** |
| `v10_ticket_dist:393` | `assert "max(1, n)" not in src` | **负**：**表达式**不得出现 |
| `v10_ticket_dist:394` | `assert "cover_bonus" not in src` | **负** |
| `mu0_prereg:191` | `assert "prereg_scheduler" in src` | **正** |
| `mu0_prereg:193` | `assert "register_scan_candidates" in src` | **正** |

### 修法不是同一种

| 类型 | 目标 | 修法 |
|---|---|---|
| **正 · 标识符/调用** | 证明**真的调用了/引用了** | **AST 查 `ast.Call` / `ast.Name` / `ast.Attribute`** |
| **正 · 表达式**（`:359` 的 `!= "llm"`） | 证明那个比较真的存在 | AST 查 `ast.Compare` + `ast.Constant` |
| **负 · 标识符** | 证明**代码里没有**（注释可以有） | **AST 全树查 Name/Attribute**，无命中 |
| **负 · 表达式**（`:393` 的 `max(1, n)`） | 证明那个调用不存在 | **AST 查 Call 结构**；或 `tokenize` 剥注释后文本匹配 |

> ⚠️ **`:393` 是唯一不能"直接换 AST"的**：
> 它匹配的是 `"max(1, n)"` 这个**源码文本形态**（含空格）。
> AST 里没有空格，必须比对 `Call(func=Name("max"), args=[Constant(1), Name("n")])` 结构，
> **或**用 `tokenize` 剥掉 COMMENT 后做文本匹配（保留原意图，只修"注释骗人"）。
> **选哪种必须写明理由**，不许含糊。

## §2 逐条验收判据（每条断言都要过三关）

**对 9 行中的每一行，必须同时满足**：

| 关 | 内容 | 方法 |
|---|---|---|
| **A. 不假红** | 当前代码上，新 AST 断言必须是**绿** | 跑该测试 |
| **B. 不假绿** | 删掉真实用法（保留注释/docstring 提这个词）→ 必须**红** | 变异注入 |
| **C. 不误报** | **只在** docstring/注释里加这个词 → 必须仍**绿** | 变异注入 |

**B 和 C 是两个方向，缺一不可**：
- 只做 B → 可能是"任何地方出现就红"，那 C 会挂
- 只做 C → 可能是"任何地方都不红"，那 B 会挂

| `:386` | 删 `channels.get("llm_can_pick")` 调用 | docstring 里加该串 |
| `:387` | 同上 | 同上 |
| `:382` | 加回 `portfolio_expected_value` 引用 | 注释里写该名 |

## §3 ⚠️ 第 5 类守卫病：AST 也要检查「覆盖了所有分支」

**这是本轮新发现的病，必须在 D-18a 里防住**：

> **「遍历了数据结构的全部元素」≠「覆盖了函数的所有分支」。**

**D-08 实证**：判据① 遍历 536 组（不是 `[:20]`）、有总数断言、报失败组号 ——
**三件套齐备**，但 `_family_pairs()` **全是 `cross|` 键**，
所以 `if gkey == "single":` 分支**从未被覆盖**。

**D-18a 的对应要求**：
```python
# 正向断言的 AST 检查必须覆盖目标函数的**每个 return / 每个分支**
# 若目标函数有 N 个分支，必须有变异能逐个打红
```

**具体要求**：交付方需给出「目标函数的分支清单」+「每个分支对应的变异与结果」。
**若某分支无变异覆盖 → 标「未覆盖」，不得算通过。**

## §4 非冗余声明必须附「唯一捕获」证据

**本轮教训**（齐交付的论据被推翻）：

> 「A 能抓到 X」**推不出**「只有 A 能抓到 X」。

**若交付方声称某条新 AST 断言「不可省」，必须附**：
1. 该变异下，**其他所有相关断言的状态**（必须列出哪些绿、哪些红）
2. 只有它红的那一档（唯一捕获）

**展示格式**：
```
变异 S2 → 判据①:绿  判据④:绿  判据⑤:红  ⇒ 判据⑤ 唯一捕获 ✅
变异 E  → 判据①:红  判据④:红  判据⑤:红  ⇒ 重叠，不能证明非冗余 ❌
```

**没有这张表，"纵深"就只是声称。**

## §9 逐行实测：`ast.unparse` 只对 **7/9** 可用（2 行会假红）

齐交付建议「用 `ast.unparse` 而不是 tokenize」。我逐行实测了，**结论是有条件成立**。

### 9.1 实测总表

| 行 | 目标词 | 类型 | 原始命中 | unparse 后 | 可用？ |
|---|---|---|---|---|---|
| `:191` | `prereg_scheduler` | 正 | True | **True** | ✅ |
| `:193` | `register_scan_candidates` | 正 | True | **True** | ✅ |
| `:359` | `!= "llm"` | 正 | True | **False** | ❌ **假红** |
| `:386` | `channels.get("llm_can_pick")` | 正 | True | **False** | ❌ **假红** |
| `:387` | `llm_can_pick` | 正 | True | **True** | ✅ |
| `:382` | `portfolio_expected_value` | 负 | — | 注入后 **True** | ✅ |
| `:383` | `expected_reward` | 负 | — | 注入后 **True** | ✅ |
| `:393` | `max(1, n)` | 负 | — | 注入后 **True** | ✅ |
| `:394` | `cover_bonus` | 负 | — | 注入后 **True** | ✅ |

**负断言的验证方式**：往**代码体**插入一条真实语句（不是注释），再看 unparse 输出能否检出。
`max(1, n)` 空格形态被 unparse 完整保留，`cover_bonus` / `portfolio_expected_value` 标识符不受影响。

### 9.2 ⚠️ 假红根因：`ast.unparse` 规范化引号（双→单）

```
原始:    return x != "llm"
unparse: return x != 'llm'        ← 双引号被改成单引号
```

**实测**：
```
'!= "llm"' in 原始源码      → True
'!= "llm"' in unparse 输出  → False
"!= 'llm'" in unparse 输出  → True
```

**所以 `:359` 与 `:386` 这两行用 unparse 会直接假红** —— 而且红得很隐蔽
（看起来像"代码被改了"，实际是**格式化差异**）。

### 9.3 这两行必须改用 AST 结构断言

| 行 | 正确形态（建议） | 说明 |
|---|---|---|
| `:359` | 查 `ast.Compare` 且 `ops=[NotEq]` 且某 `comparator` 是 `Constant("llm")` | 语义：**代码里存在"与 'llm' 不等"的比较** |
| `:386` | 查 `ast.Call`，其 `func` 为 `Attribute(attr="get")`，且 `args` 含 `Constant("llm_can_pick")` | 语义：**真的调用了 `.get("llm_can_pick")`** |

**注意 `:386` 现在的 `or "llm_can_pick" in src` 是弱兜底** ——
按语义它想验的是「`channels.get("llm_can_pick")` 这行短路存在」。
AST 版应当**去掉 or 弱化**，只认真实调用；否则与 `:387` 重复。

### 9.4 结论

> **`ast.unparse` 是"剥注释+剥 docstring"的便捷手段，但它会重写字符串字面量的引号形式。**
> **凡断言的目标文本里含引号，一律不能走 unparse，必须走 AST 结构。**

**这条已加入 §2 的三关之外，作为第 4 关**：

| 关 | 内容 |
|---|---|
| **D. 不假红（格式化）** | 新断言在**当前代码上**必须绿；若用 unparse，须确认目标文本在 unparse 输出中仍存在 |

**关 D 独立于关 A**：关 A 是"跑测试看绿不绿"，关 D 是"**为什么**绿"——
**如果绿是因为目标文本消失了（而不是因为代码正确），关 A 会误判为通过。**
