## §2 逐处判定（3 处）

### ① `test_mu2_frontend_llm.py:90` —— **真实风险，需要改**

```python
js = _js_code()          # 已剥注释
assert "照常出号" in js
assert "不受系统配额限制" in js or "不受配额" in js     # ← 这一行
```

**实测**：
```
"不受配额" 在 app.js 中只出现于 4108 行的 // 注释：
    /** 今日共享通道用量。自备 Key 不受配额限制，因此不显示这条。 */
```

**问题**：`_js_code()` 已剥注释，所以这个 `or` 分支**永远为假**。
它只是 `"不受系统配额限制" in js` 的冗余兜底，**不构成风险，但也不起作用**。

**更值得注意的是这个测试自己的 docstring**：
```
js = _js_code()   # 剥离注释：这两句在注释里也出现，用 _js() 属假绿
```
**作者已经知道这个坑并修过** —— 说明这类问题**真实发生过**，不是理论风险。

**处置**：删掉 `or "不受配额" in js`（死分支），或改成剥注释后仍有效的形态。

### ② `test_v14_naming_discipline.py:162` —— **意图即依赖注释，不是缺陷**

```python
def test_backend_discipline_text_intact():
    """后端「不得叫可用规律」的纪律文本必须还在。"""
    src = (REPO / "lottery" / "routes_predict.py").read_text(encoding="utf-8")
    assert "不得" in src and "可用规律" in src
```

**实测**：`可用规律` 在 `routes_predict.py` 中出现 **6 次，全部是注释**。

**变异验证**（删掉含目标词的 6 行注释）：
```
FAILED test_backend_discipline_text_intact   ✅ 敏感
```

**判定**：**这个断言的意图就是「验证纪律文本（注释）还在」**。
它不是检查代码行为，而是检查**书面依据没被删**。
**所以它「依赖注释」是设计使然，不是缺陷。**

⚠️ **但它有一个真实风险**：`getsource` 无法区分「注释」与「字符串字面量」。
若有人把这段纪律写成**输出给用户的文案**，断言同样通过 —— 而那恰恰是 D-12 要禁止的。
**建议**：加一句注释写明「本断言有意检查注释，不检查代码」。

### ③ `test_v14_naming_discipline.py:122` —— **同类，但方向相反**

```python

assert "rule_evidence" not in src
```

**实测**：`rule_evidence` 在 `routes_predict.py` 中**零次出现**（代码和注释都没有）。

**但如果将来有人在注释里写「不要用 rule_evidence」→ 断言会假红。**

**处置**：改成剥注释后判断（与本项目其他负断言一致），或至少记录这个风险。

## §3 为什么「假绿/假红」在 B 类里比 A 类难量

A 类（Python 源码）：`getsource` 返回的就是代码 + docstring，**两层，容易剥**。

B 类（外部文件）：三种语言各有注释语法，且**注释与代码在同一文本里交错**：
```
app.js : // 与 /* */（且 // 要避开 http://）
html   : <!-- -->
css    : /* */
```
**一旦剥错，就会把字符串里的 `//` 当注释切掉** —— 那比不剥更糟。

**这就是为什么本项目已经有 4 个文件各自写了一遍 `_js_code()`：**
```
test_mu2_frontend_llm.py:21
test_v10_channel_wiring.py:29
test_v10_frontend_cards.py:38
test_w08_frontend_auth.py:41
```
**四个实现，可能四种细微不同的行为** —— 这本身是「第二真源」的形态。

## §4 建议的 D-18b 方案（分三层，按性价比）

| 层 | 内容 | 工作量 | 收益 |
|---|---|---|---|
| **① 合并 `_js_code` 实现** | 4 个副本 → `tests/_source_assert.py` 一份 | 小 | 消除第二真源 |

| **③ 加元守卫** | B 类「用 `read_text` 做子串断言」的**总数不增长**（基线 115） | 小 | **防新增**，不追求清零 |

**理由**：99 处里有 96 处目标词同时出现在代码里（不是纯注释），
**改它们收益很小**，而改动 16 个文件的风险远大于收益。

> **「115 处」听起来很多，但「真实风险 1 处、失效死分支 1 处、需加说明 2 处」才是实际工作量。**
