## §0.0 验收的元纪律（管的是验收人自己）

> 以下两条不限对象，**对 Lead、交付总监、各工程师、以及我自己同等适用**。
> 它们管的是「判断权」从哪来，而不是「判断结果」是什么。

### 元纪律 1 —— 引用任何数字前，先分清它是「谁测的」

**规则**：

1. **自己跑过的** → 可以写「实测」，必须附命令 + 原始输出。
2. **别人给的** → 必须写成**「转述自 X（文档/消息）」**，**不得写成实测值**。
3. **文档/方案里的自述数字** → 一律视为**未验证**，除非找到产生它的脚本与输出。
4. 报告里出现任何数字，问一句：**「这个数是谁的？我复现过吗？」**
   复现不了 → 标「未验证」，不许标「一致」。

**实证代价**（本项目真实发生）：
- 「53.6% 代码无监工」—— 方案自述，被当实测写进看板；**实测私有函数是 60 个，分母都可疑**。
- 「16.73 元」—— 从未复现的推算，被写进验收标准，**而刘工正照着它施工**。
- 「`0.40 <= x <= 0.65`」—— 区间看似"实测可得"，实际**什么都放行**。

**最隐蔽的一种**：数字**碰巧是对的，但不知道对在哪**。
例：我报「冷启动 7.41s」，后来发现那次恰好清过磁盘缓存 ——
**结果对、机理不明 = 不可复现 = 与结果错等价**。

### 元纪律 2 —— 判「某断言/某测试无效」之前，必须打开函数读完整上下文

**规则**：

1. 不得凭**单行形态**下判断（看到 `or True`、看到一行 `assert`、grep 命中数量）。
2. 必须读：**函数体 + 前置 setup + 相邻用例**，确认它到底在测什么。
3. 「注释说见下一条」→ **必须真的翻到下一条**，不许"没找到就判不存在"。
4. **谁的证据层级更高，听谁的** —— 不是谁的职级更高。
   - 有 ctx 构造 + 变异实证 > 只有一行 grep 命中的形态判断。

**实证代价**（本项目真实发生）：
- 判 `test_check_shape_accepts_normal` 为「仅一行、可删」—— 实读后它有 ctx 构造与业务含义。
- 判「下一条静态断言不存在」—— 实际 `test_no_bare_ev_ratio_field_in_ticket_distribution` 就在下面。
- 判 M3 变异「挂起」—— 实跑 `1 failed, 54 passed in 22.6s`，且源码里根本没有无界重试。

> **两条元纪律的共同点**：
> 元纪律 1 防「**没测过**就当实测」，元纪律 2 防「**没看全**就当结论」。
> 今天所有误判都落在这两类里 —— **包括我自己的**。

## §0 三条红线

红线不是"注意事项"，是**一票否决**。触线即打回，不接受解释。

### 红线 1 —— 测试只增不减

```
1358 passed, 24 skipped, 1 xfailed
```

- `passed` **少于 1358** → 打回。
- `skipped` **多于 24** 且无书面理由 → **隐性减测试**，等同删测试，打回。
- `xfailed` **多于 1** 且无书面理由 → 同上，打回。
- 新增测试允许增加上述数字，但**必须说明增量对应哪个行为**。

> 只盯 `passed` 是不够的。把一条测试改成 `skip` 或 `xfail`，`passed` 会掉，
> 但把三条测试合并成一条 skip 的测试，`passed` 可能看不出来。**三个数一起看。**

### 红线 2 —— 口径常量不得写死

`306 / 72350 / 0.05 / 52.3% / 15.625%` 这类数字，**必须由计算得出**，
不得以字面量出现在生产代码路径里。写死 = 无法随数据更新而更新 = 假完成。

（例外：`docs/` 下的说明文档、测试里作为**期望值**的断言常量。）

### 红线 3 —— 声称"已实现"必须被实际调用过一次

只给代码 = 未完成。必须附**实际调用证据**：端点 `curl` 响应、函数 REPL 输出、
页面实际渲染结果。**没有输出 = 没有实现。**

## §4 基线（硬地板）

### 4.1 基线有两个口径 —— 必须标明是哪一个

| 口径 | 是什么 | 用途 |
|---|---|---|
| **HEAD 口径** | 在独立 worktree 里跑 `HEAD`，不含任何未提交工作 | 证明**已提交部分**干净 |
| **工作区口径** | 在项目目录跑当前工作区 | 证明**当前集成状态** |

两者数字不同是**正常的**，但报告里**必须写明哪个是哪个** —— 否则数字之间无法比对。

| passed | **1358** |

| 耗时 | ≈ 480s |

### 4.3 工作区口径


工作区数字随成员提交变化。**判定下限仍是 `passed ≥ 1358` 且 `failed == 0`。**
高于 1358 是正常的（新增测试），但**必须能说明增量对应哪些行为**。

### 4.4 ⚠️ worktree 里跑测试的三个环境陷阱（实测踩到）

1. **`.venv` 不跟随 worktree** —— 它被 `.gitignore` 忽略，worktree 里没有。
   `tests/test_db_guard.py:19` 硬编码 `ROOT / ".venv/bin/python"` 起子进程，
   于是 3 条测试报 `FileNotFoundError`，**看起来像 HEAD 有缺陷，其实是环境缺失**。
   → 解法：`ln -s <main>/.venv .venv`。
2. **`data/` 目录不存在** —— 同上，未跟踪。
3. **判定前必须先排除"环境型失败"** —— 凡 `FileNotFoundError` / `No module named`
   一律先查环境，不要直接判 HEAD 有缺陷。

> **教训**：worktree 是"干净 checkout"，不是"可运行 checkout"。
> 看到 worktree 里的失败，**先问是不是环境**，再问是不是代码。

## §5 全跑纪律（本项目的血泪条款）

### 5.1 一律全跑，不许单跑交差

本项目有**镜像双源前科**：`monkeypatch` 只打桩薄壳、真源未变，
单跑该文件通过、全量跑才失败，且**依赖测试顺序**。

因此：**单跑通过不构成完成证据**。任何"改完我跑过了"必须附**全跑**输出。

### 5.2 ⚠️ 不许只看 exit code

**这是本闸门最容易被绕过的一条。**

实测（见案例 #1）：pytest 收集阶段崩溃时，原始退出码是 `2`，
但命令写成 `pytest ... 2>&1 | tail -20` 后，管道取的是 `tail` 的退出码 **0** ——
**一场灾难被当成通过**。

规则：

1. **必须解析 stdout 里的 `passed` 计数**，不许用 exit code 当唯一判据；
2. `passed` 字样**缺失** → 判 **failed**（说明收集阶段就崩了）；
3. 解析出的 `passed < 1358` → 判 **failed**；
4. 若用管道，shell 必须 `set -o pipefail`，或改用 `PIPESTATUS[0]`。

```bash
# 正确写法
set -o pipefail
OUT=$(.venv/bin/python -m pytest tests/ -q --ignore=tests/frontend 2>&1)
echo "$OUT" | tail -20
echo "$OUT" | grep -qE '^[0-9]+ passed' || { echo "GATE FAIL: 无 passed 计数（收集崩溃）"; exit 1; }
```

### 5.3 冒烟前置检查（秒级，先于全跑）

```bash
.venv/bin/python -c "import lottery.engine, lottery.api_app, lottery.routes_predict; print('imports ok')"
```

**必须输出 `imports ok`。** 放在全跑之前，秒级捕获循环导入 / 模块缺失，
不用等 8 分钟才发现。

### 5.4 结构性变更的"收集阶段"必须单独校验

拆包、改目录、改导入结构这类变更，**`pytest --collect-only` 必须单独跑一次**：

```bash
.venv/bin/python -m pytest tests/ -q --ignore=tests/frontend --collect-only
```

期望：`1445 tests collected` 且 **0 error**。

理由：收集阶段崩溃时**一条都跑不了**，而它和"跑了几条但失败"在输出上完全不同。
拆分类变更必须**改一步、验一次收集、再全跑**，不得批量改完再测。

## §5.5 冷启动耗时必须在验收范围内

**触发事件**：`/api/portfolio/popularity` 冷启动首次请求实测 **12.15s**（真实容器 28.55s），
热态 **0.012s**，差约 **1000 倍**。

**这 28 秒里：所有数字都正确、同屏一致、算术闭合 —— 但用户等了半分钟。**

**我们的验收标准全部是「值对不对」，一条也抓不到「多久给」。** 这是验收盲区，不是实现缺陷。

**规则**：

1. **凡自动触发的用户可见数据，必须实测「首次请求耗时」**（干净实例、冷态）。
2. **冷启动 > 3s 即阻断**（P1 以上）。
3. **不许用热态数据糊过去**。测量方法：
   ```bash
   # 起一个干净进程，只打一次
   .venv/bin/python - <<'PY'
   import time, subprocess
   # 或在独立进程内直接调端点函数，记录首次调用的 wall time
   PY
   ```
4. 报告里必须写「第 1 次 / 第 2 次」两个数字。

## §5.6 ⚠️ 测试超时不得低于缺陷阈值

**触发事件**：`v14_honest_bounds_ui_probe.py:308` 用 `wait_for_function(timeout=20000)`，
而被测接口冷启动需 **28.5s** —— **20s 卡在 28.5s 之下**。

> **测试超时设得比缺陷阈值低，等于给缺陷装了一个消音器。**

后果不只是"漏检"，而是**flaky，且 flaky 方向正好掩盖缺陷**：
慢的时候测试超时失败（看起来像环境抖动），重跑又快又过（看起来没问题）。

**规则**：

1. 任何带 `timeout` 的探针/等待，**超时值必须 > 已知的最坏耗时**（含冷启动）。
2. **审查探针的全部 `timeout=` 值**，逐个判断它**等待的目标依赖哪一次请求**，
   不得用"这条路径大概不慢"来豁免。
3. 探针里不得出现"魔法数字超时" —— 必须写明**为什么是这个值**、对应哪条路径的最坏耗时。

### ⚠️ 反直觉的对称陷阱：超时**太长**同样掩盖缺陷

- **太短** → flaky，看起来像环境抖动（漏检）
- **太长** → 缺陷在超时内跑完、测试变绿（**同样漏检**）

实例：`:319` 的 20s 覆盖了 9.29s 的全额阻塞，测试**通过**，但用户等了 9 秒。

> **所以「调大超时」不是修法。** 正确做法是**独立断言耗时本身**：
> ```python
> elapsed = ...
> assert elapsed < 3.0, f"首次请求 {elapsed:.2f}s，超过 3s 阈值"
> ```
> 超时只用于"防挂死"，功能上"多快算合格"必须单独断言。

### 逐处判定的正确方法（本轮实证）

`v14_honest_bounds_ui_probe.py` 共 8 处超时。**不能笼统说"都低于 28.5s 所以都危险"** ——
要追每个等待的**填充来源**：

| 等待目标 | 谁填充 | 依赖请求 | 最坏耗时 | 判定 |
|---|---|---|---|---|
| `#honestBounds` | `fillHonestBounds(d)` | `blue-coverage` | 2.84s | 15s 够 |
| `#hbSource` 文案 | 同上 | `blue-coverage` | 2.84s | 20s 够 |
| `#blueCovBody` | `renderBlueCoverage(d)` | `blue-coverage` | 2.84s | 20s 够 |
| `#popBody` | `loadPopularity()` | **`popularity`** | 9~28s | ⚠️ 唯一风险点 |
| 滚动/选择器类 | 纯前端 | **无网络** | <1s | 全部安全 |

**只有 1 处真的依赖慢路径，不是 8 处。**

## §5.7 测冷启动必须先清缓存，否则测的是热态

**触发事件**：同一脚本连跑三次，冷启动测得 `27.25s → 0.53s → 0.39s`，**差 70 倍**。
根因：`data/popularity_model.json` 是**跨进程持久缓存**，第一次跑完就写盘，后续进程直接命中。

**规则**：

1. 测"首次请求耗时"前，必须删除对应的持久缓存，**并确认文件 mtime 已变化**：
   ```bash
   rm -f data/popularity_model.json
   ls -la --time-style=+%H:%M:%S data/popularity_model.json 2>&1   # 应为「不存在」
   # 跑一次后再看 mtime，确认是这次写的
   ```
2. 缓存文件名/位置必须查明（`grep -n "_CACHE_FILENAME\|_cache_path" lottery/*.py`），
   **不许假设"新进程 = 冷启动"**。
3. 报告里必须写「清缓存后的第 1 次」和「第 2 次」两个数，并注明缓存文件路径。

> **教训**：我上一轮报「首次 7.41s」结果碰巧是对的，但**不知道对在哪** ——
> 那次恰好清过缓存。**"结果对但不知所以"和"结果错"一样危险**，因为它不可复现。

## §5.8 请求路径不得同步做长耗时工作（含"限时等锁"的伪解）

**触发事件**：`get_model_with_deadline(timeout=2.0)` 只对**等锁**设超时，
拿到锁后**仍会自己 `fit()`**。清缓存后实测首次请求 **9.29s 返回 200**（不是 503）。

**规则**：

1. 用户请求路径**不得包含**秒级以上的同步计算（拟合、训练、批量 IO）。
2. **"限时等锁"不是解**：它只限制了排队时间，没限制"拿到资源后自己干活"的时间。
   正确形态是**永不自做重活** —— 拿不到现成结果就降级（503/空态），重活交给后台预热。
3. 验收时必须测**"预热线程尚未取锁"的竞态窗口**：
   ```bash
   rm -f data/popularity_model.json   # 强制冷
   # 立即打请求，测耗时 —— 这才能复现"请求先于预热取到锁"的路径
   ```
4. 竞态类修复必须给出**时序图**（t=0 预热进来 / t=0.3 请求进来 / 谁先取到锁），
   不接受"加了超时所以安全了"这种结论。

### ⚠️ `timeout` 参数的作用域必须在签名/文档里写明

**`timeout` 的存在本身会暗示「超时后问题就解决了」。它没有。**

本项目实证：
```python
def get_model_with_deadline(timeout: float = 2.0) -> PopularityModel:
    # timeout 只作用于 acquire —— 即"排队等别人"
    acquired = _CACHE_LOCK.acquire(timeout=timeout)
    if not acquired:
        return PopularityModel()          # ← 超时分支：降级
    try:
        return _get_model_locked(...)     # ← 拿到锁后：全额 fit，timeout 管不到
    finally:
        _CACHE_LOCK.release()
```

**必须以注释或 docstring 明写**：

> `timeout` **只作用于 `acquire`，不作用于 `with lock:` 块内的执行**。
> 拿到锁之后哪怕跑 10 分钟，`timeout` 也不会介入。

**验收动作**：凡看到 `timeout=` 参数，先问一句
**「它管住的是等待，还是工作？」**
管不住工作的超时，只是把"无限等"变成"有限等"，
不改变"最后还是要自己做"这件事。

## §5.9 ⚠️ 全量失败必须**先复现**再上报（并发期强制）

> 这是我自己栽出来的纪律。2026-10-21 一天内我报了 **3 次**"地板破了"，
> 其中 **2 次是别人正在编辑的中间态**（14:08 的 NameError、14:14 的 5 failed）。

**现象**：我在 A 时刻跑全量 → N failed → 立刻上报"地板破"；
对方在 A+6 分钟提交完 → 我复跑 → 0 failed。
**两个数字都是真的，但我把"时刻快照"当成了"结论"。**

**规则（并发期强制）**：

1. **任何全量失败，上报前必须复现一次**（立刻重跑全量，或跑失败文件的子集）。
2. **复现不了的失败，写「瞬时失败（未复现）」**，不得写成「缺陷」。
3. 复现时**记录两个时刻**：`观察时刻` 与 `复跑时刻`，以及两次的 mtime/`git status`。
4. 只有**在干净 worktree 的当前 commit 上复现**，才可以判「缺陷」。
5. 判"构造性/故意"的失败（TDD 中先写测试后写实现）→ 看测试文件 mtime 是否**晚于**实现文件，
   若是，大概率是中间态，等实现落地再验。

**分诊表**：

| 现象 | 判读 | 处置 |
|---|---|---|
| 全量 N failed，单跑该文件 0 failed | **顺序污染**（真实缺陷，镜像双源同族） | 必须定位前序污染源 |
| 全量 N failed，立即复跑 0 failed | **瞬时中间态** | 记「未复现」，不判缺陷 |
| 全量 N failed，复跑仍 N failed | **缺陷** | 上报，附两次时刻 |
| 干净 worktree（HEAD）上 failed | **已提交缺陷** | 最高优先级 |
| 干净 worktree 上 passed，工作区 failed | **未提交改动引入** | 找改动人，不是找代码 |

**今天的实证对照**：

```
14:08:31  2 failed  → 我报 P0 NameError   → 14:14 复现: 已修复（重构中间态）
14:14:25  5 failed  → 我未上报（先查）    → 14:18 单跑该文件: 16 passed（顺序/中间态）
                                             14:20 全量: 1569 passed, 0 failed
```

**注意 14:18 那次的另一半**：单跑 `test_v14_popularity_coldstart.py` → 16 passed，
而全量里它 5 failed。**这属于"顺序污染"候选** —— 但 14:20 全量 0 failed，
说明那 5 条是**该文件当时正被编辑**（新测试已写入、实现未落地），不是顺序污染。
**两种情况的判别方法：看复跑是否稳定。** 顺序污染会稳定复现，中间态不会。

> **一句话**：**「我看到了失败」不等于「存在缺陷」。**
> 前者是观测，后者是结论。**跨过这一步的动作就叫复现。**

## §6 变异测试清单（我的主要武器）

### 为什么必须做

"新增了守卫测试"和"守卫真的能抓住缺陷"是两件事。
**注入缺陷后测试仍全绿 ⇒ 测试是假的。** 这是抓"假测试"最有效的手段。

### 6.1 判定标准

| 变异结果 | 判定 |
|---|---|
| 注入后 **failed** | ✅ 测试有牙 |
| 注入后仍 **passed** | ❌ **假测试**，立即打回并指出缺哪个守卫 |
| 注入后 **崩溃/挂起** | ⚠️ 需单独解释（可能暴露死循环等更严重问题） |

### 6.2 必须复原

每个变异做完**立即复原**，并以 `git diff` 为空作为复原证据：

```bash

git status --short     # 不得残留
```

**未复原即离开工作区 = 污染他人验收 = P0 事故。**

#### 6.2.1 ⚠️ 「复原」必须用输出证明，不能只看退出码（严QA 实测踩坑）

`git diff --stat` 为空的**前提是那个仓库有对应基线提交**。
若在 `git archive` 重建的隔离副本里作业，副本的 git 仓库是空历史，
`git checkout -- .` **静默无效**、`git diff` **永远为空** ——
两者都在撒谎，而退出码都是 `0`。

**我的实际事故**：M1 跑完后执行 `mutate.py revert`，命令返回 0，`git diff` 为空，

## §6.4 未跟踪的测试文件不会随 `git stash` 消失

**这是本轮最昂贵的一条教训（案例 #2）。**

未跟踪（`??`）的测试文件**不受 `git stash` 影响**，而它测的实现若已被改（或已提交），
就会一起 `stash` 走 —— 结果是**功能消失、测试留下**。

因此「测试红了」有**两种**可能，必须先分诊再定性：

| 可能 | 判别 | 处置 |
|---|---|---|
| ① 代码真的坏了 | `grep 功能名 lottery/ routes_*.py` **有**命中 | 按缺陷处理，打回 |
| ② 代码被 stash 走了、测试还在 | `grep` **零命中** + `git stash list` 非空 | **不是缺陷**，是工作区事故 |

```bash
# 分诊两连
grep -rn "功能名" lottery/ routes_*.py   # 零命中？
git stash list                            # 非空？
```

**任何时候 `git stash` 前，必须先看 `git stash show --stat` 列出的文件清单，
确认没有夹带与当前事故无关的改动。**

## §6.5 并发改动期间的工作区状态，不得作为结论依据

**触发事件**：2026-10-21 12:40 前后，`engine.py` 正被改名为包，我在该窗口内观察并转述
「`engine.py` 已删除、`lottery/engine/` 已建」，随后被当作**持续事实**传播，
衍生了「保 `engine.py:1180` 必须先拿映射」等错误推论。实际处置已完成回滚。

**规则**：

1. **工作区是流动的，不是事实源。** 并发改动期间观察到的一切状态，都只是**某一时刻的快照**。
2. **引用任何状态，必须注明观察时刻**，例如「13:02 实测」。
3. **不得由瞬时状态推导持续性结论。** 「此刻是 D」≠「已被删除」，也 ≠「拆分进行中」。
4. **使用前重测。** 转述超过 5 分钟的状态必须重跑 `git status` / `ls` 再引用。
5. **优先引用不变量**而非状态：
   - ❌「engine.py 已删除」→ 会过期
   - ✅「`import lottery.engine` 失败」→ 可随时重测
   - ✅「`lottery/engine/` 目录存在」→ 可随时重测

**反直觉之处**：这条纪律**不是防别人骗你**，是**防你信自己五分钟前的观察**。
后者更难防，因为它不需要怀疑任何人，只需要怀疑自己。

**推论（写入 §4.4 的一条强化）**：worktree 里的异常，先怀疑环境（缺 `.venv` / `data/`），
再怀疑代码；工作区里的异常，先确认**观察时刻**，再确认**观察对象**。

## §6.6 `job_output` 无输出 ≠ 进程挂起

**触发事件**：2026-10-21，注入 `pass_constraints` 奇偶分支反转后，后台跑测试 12 分钟无输出，
我据此判定「挂起」，并给出「重试 60 次耗尽 ⇒ 死循环」的机理分析。**两者都是错的。**
复现结果：同一注入正常变红（`1 failed, 54 passed in 22.6s`）；
源码里 `sample_stat_ticket` 60 次后返回 `None`，`battle.py` 的 `while` 有 `guard` 上限 —— **无无界重试**。

**规则**：

1. **判定"挂起"必须看进程状态**，不能只看日志缓冲：
   ```bash
   ps -o pid,stat,%cpu,etime,cmd -p <pid>   # 有 CPU 占用 = 在跑，不是挂
   ```
2. **看堆栈用 `faulthandler` 或 `SIGABRT`**：
   ```bash
   timeout -s ABRT 60 .venv/bin/python -m pytest ...   # 崩时打印全部线程栈
   ```
3. **命令行直接跑**（前台、带 `timeout`），不要用后台 job 判断是否挂起 ——
   后台 job 的输出是流式的，缓冲会导致"看起来没动静"。
4. **机理结论必须能被代码证实。** 说出"死循环"之前，必须指出**具体哪一行是无界的**。
   指不出来，就是猜测，不是诊断。

> 这两条（§6.5 / §6.6）的共同点：**我都是在"信息不足以支撑结论"时下了结论。**
> QA 的价值在于判得准，不在于判得多。**宁可写"未验证"，不可写"已确认"。**


**我的独立核实**：

| 核实项 | 转述值 | 我的实测 | 结论 |
|---|---|---|---|
| 崩溃现象 | `Interrupted: 10 errors during collection` | 已复原，当前无此现象 | — |

| 收集崩溃时 exit code | **0** | pytest 原始退出码 **2**；`\| tail` 管道下才是 **0** | ⚠️ **转述不准确** |

**⚠️ 对"exit code 是 0"的更正（重要）**：

实测四种写法，pytest 自身**始终返回 2**：

```
mode='-q'                        -> exit=2
mode='--collect-only -q'         -> exit=2
mode='-q --ignore=tests/frontend'-> exit=2
pytest ... | tail -2             -> PIPESTATUS[0]=0   ← 管道取的是 tail 的退出码
pipefail + pytest ... | tail -2  -> 2
```

**所以不是 pytest 的缺陷，是管道吞掉了退出码。**
这正是 §5.2 存在的理由：**任何脚本化检查若写成 `pytest | tail`，都会把灾难当通过。**
根因认识错了，防护就会写错地方 —— 以为要绕开 pytest 的 exit code，
实际要防的是自己的管道。

**永久防护（建议守卫测试）**：

```python
assert consts["ev_single"] == pytest.approx(round(expect, 6), abs=1e-9)
```

否则口径一变，守卫就从"抓缺陷"退化成"抓文档"。

## §6.7 守卫的「输入 vs 事实」总纲（2026-10-21 一整天踩出来的）

> **一句话**：**判据的输入，和它想验证的事实，是同一个东西吗？**
> 不是 ⇒ 它会被某种「看起来像」的东西骗过去。

### 6.7.1 已证实的 8 种绕过手法

| # | 手法 | 实例 | 判据被骗的方式 |
|---|---|---|---|
| 1 | `\| tail` 吞退出码 | `pytest ... \| tail -20` | 退出码取的是 tail 的 |
| 2 | `git stash` 收走工作 | 30 条测试红的实现睡在 stash 里 | 以为"代码坏了" |
| 3 | 白名单静默丢字段 | `sixth_mode` 写了但被组装层丢弃 | 以为"字段不存在" |
| 4 | 无基线仓库的 `git diff` | `git archive` 副本里 diff 永远为空 | 以为"已复原" |
| 5 | 环境假设替换事实 | 「容器内没有 httpx」→ 放弃 HTTP 测试 | 以为"做不到" |
| 6 | 注释冒充代码 | `assert "X" in src` 被 docstring 骗 | 以为"代码调用了" |
| 7 | 抽样代替全遍历 | `[:20]` 冒充 536 组 | 以为"逐组比对了" |
| 8 | **作用域边界选窄** | AST 只扫函数级，漏模块级变量（36 vs 115） | 以为"统计全了" |

**共同点**：**动作发生了，但没有任何一步确认它作用在正确的对象上。**

### 6.7.2 变异实验的立场（比"作者/非作者"更本质）

> **执行变异前先声明立场：「我要找的是守卫的洞，不是守卫的证据。」**

- 只做「破坏目标」的变异 ⇒ 证明的是**接线**（守卫确实被调用了）
- 能做「绕过输入」的变异 ⇒ 才检验**判据**（守卫的输入对不对）

**实例**：D-08 五档变异中，A/B/C 是破坏目标，**D（`real*2`，无裸常数）/ E（删真源只留兜底）** 是绕过输入 ——
**而 D/E 才是唯一发现新缺口的两档。**

**关键**：作者也能构造"绕过输入"型变异，**前提是他愿意假设"我的守卫是错的"**。
差别不在身份，在立场。

### 6.7.3 写判据的标准动作：假完成推演

```
① 写判据时问：「如果我要假装满足它，最省力的做法是什么？」
   → 那件事就是这个判据必须堵的洞。
② 然后去读现有的同类守卫 —— 它很可能已经掉进那个洞里。
③ 写完后再扮演一次"最懒的交付方"，试一次能否通过。
```

**单有 ② 只能发现"别人犯过的错"；加上 ① 才能发现"还没人发现的错"。**

**实例**：写 D-08 预案时写「交付方须贴遍历 536 组」→ 反问「贴个 `[:20]` 也能说逐组比对了」
→ 去看现有测试 → **真的就是 `[:20]`**。

### 6.7.4 源码结构断言一律经 AST，不得用字符串 `in`

**理由**：`getsource` **包含 docstring**；"源码里出现过某字符串"与"代码实际做了某事"
之间隔着**注释、docstring、变量名、死代码**。

```python
# ❌ 会被 docstring 骗
assert "_family_pairs()" in inspect.getsource(fn)

# ✅ AST 检查真实 Call，并剥掉 docstring
tree = ast.parse(textwrap.dedent(inspect.getsource(fn)))
body = tree.body[0].body
if body and isinstance(body[0], ast.Expr) and isinstance(getattr(body[0], "value", None), ast.Constant):
    body = body[1:]                      # ★ 剥 docstring（防反向误报）
calls = {n.func.id if isinstance(n.func, ast.Name) else getattr(n.func, "attr", "")
         for n in ast.walk(ast.Module(body=body, type_ignores=[])) if isinstance(n, ast.Call)}
```

**注意两个方向**：
- **假通过**：删真实调用、注释里留着 → 仍绿
- **假通过**（反向误报）：注释里写「本函数不使用 X」→ 无辜变红，**逼人改注释而不是改代码**

**统计"待 AST 化"的位置也必须用 AST，不能用 grep 数。**
本项目实测：`grep 'assert.*in src'` → 16~17 处；**AST 按变量来源分类 → A 类（Python 源码）10 处 / B 类（JS/HTML 文本）115 处**。
用 grep 数 AST 化目标，本身就会漏掉变量名变体（`code`/`js`/`blob`）。

### 6.7.5 往返判据：抓「两半各自正确、接口对不上」

任何「产出方 → 消费方」的配对，必须测**往返**：

```python
for key in producer_output_keys:
    assert consumer_key_of(construct(producer, key)) == key
```

**实例**（D-08）：`_group_key_of` 与 `_family_pairs` **各自都正确**，
但没人测「前者产出的键能否在后者里查到」。
实测：把 `_group_key_of` 改回「只取 mode」→ 返回 `cross|0`，不在 `_family_pairs()` 里
→ `_group_checked` **静默退回 `max(n_in_group, 1)`，m 全错，而 m 比对测试仍全绿**。

**这类问题任何单侧测试都抓不到。** 适用于：D-02 拆分后的薄壳与子模块、API 与前端字段、序列化与反序列化。

### 6.7.6 「修复 vs 放水」：**判定看真源，答辩看方向分布**

> **这一节原来写成了一条判据，是错的。** 齐交付指出后我复核，确认：
> **它在判据① 通过后信息量归零 —— 那不是判据，是注释。**

#### 【判定】机器执行，通过 / 不通过

```python
# 唯一判据：m == 真源，逐组比对（见 §6.7.5 的往返思想）
for gkey, real in _family_pairs().items():
    assert _group_checked(gkey, ...) == real
```

**通过 ⇒ 修复成立，与"方向分布"无关。**
若真源的真值恰好全部小于旧常数，"100% 变松"也是**正确**的 —— 因为真源就是那样。
**把"双向修正"当判据会误伤这种情况。**

#### 【答辩】对人 / 对外沟通时使用

若有人质疑「你们是不是放宽了门槛」，用方向分布回应：

```
统一放宽 ⇒ 需要解释（可能是真源如此，也可能真是放水）
双向修正 ⇒ 有力回应（放水不会双向）
```

**但这只是说服工具，不是判定依据。**
D-08 实证：`78.4% 变松 / 21.6% 变严（最严收紧 17 倍，中位比值 0.26）`。

#### 判据冗余的元规则（本次逼出来的）

> **写判据时先问：这条判据在什么条件下会「必然通过」？**
> **若存在一条更强的判据能让它的信息量归零 —— 它不是判据，是注释。**

**这条防"判据通胀"**：堆很多条看起来严谨的断言、实际互相冗余，
读的人会以为覆盖很全，而主判据只有一条。

#### ✅ 非冗余的正例（实测，不是推断）

**判据⑤（AST 实际调用真源）确实不可省，但理由不是"能抓变异 E"** ——
实测变异 E 时**判据① 也红了**，两者对 E 是重叠的。

**它真正的独立价值在 `single` 分支**：
```bash
$ 统计 _family_pairs() 的键前缀 → {'cross': 536}   # 全是 cross|
```
**判据① 遍历的是 `_family_pairs()` 的键，因此从不覆盖 `single` 分支。**

实测三个变异：

| 变异 | 判据① | 判据④(裸 int) | 判据⑤(AST 调用) |
|---|---|---|---|
| S：`single` 分支 = 字面量 `306` | ❌ 不覆盖 | ✅ 红 | ✅ 红 |
| **S2：`single` = `int(len(pairs) * 0.5712)`（float 伪值）** | ❌ 不覆盖 | ❌ float 不算 int | **✅ 唯一红** |
| E：删 `_family_pairs` 调用 | ✅ 红 | ✅ 红 | ✅ 红 |

**S2 是判据⑤ 唯一捕获的变异（1 failed, 28 passed）——这才是它存在的理由。**
**「两条各自能独立捕获」必须用变异证明，不能靠"它们看起来不同"推断。**

### 6.7.7 变异实验的假阴性：注入没生效 ≠ 守卫没牙

**我的实际事故**：验证 `:199` 守卫时第一次注入锚点写错，**注入失败但测试"通过"**，
我一度以为守卫没牙；换正确锚点后确认为红（有牙）。

> **「测试通过」可能是"注入没生效"，不是"守卫没牙"。**

**规则**（与 6.2.1 的"复原要证明"对称）：
- **注入后**：用 `grep` 命中变异文本 / `md5` 变化 / 编译错误 —— 三选一证明真的写进去了
- **复原后**：用 `grep` 命中真值 / `md5` 一致 —— 证明真的改回来了
- **两端都要证明**，因为"通过"可以被两种完全不同的原因造成
