## 门 1｜冷启动时效门（交付门第 4 条增补）

### 1.1 规则原文

> 凡**自动触发**的用户可见数据，必须实测**首次请求耗时**；冷启动 **> 3 秒即阻断**。
> 判据：起干净实例 → 首次请求计时 → **不许用热态数据糊过去**。

### 1.2 为什么需要它：原有第 4 条的盲区

第 4 条红线是「端到端对同一量取真实值交叉核对」，它抓的是**值对不对**。这次 28.55 秒的缺陷里：

| 检查项 | 结果 |
|---|---|
| 所有数字是否正确 | ✅ 全对 |
| 四对同屏一致性 | ✅ 全部归零 |
| 算术闭合（`20 − 3.125 = 16.875`） | ✅ 成立 |
| **用户等了多久** | ❌ **28.55 秒** |

**四项全绿，用户仍等了半分钟。** 这就是第 4 条抓不到的那一维。

### 1.3 可执行判据（照抄即可跑，不需要改代码）

```bash
# ① 起干净实例（当前进程内缓存全空）
#   注意：必须用隔离库副本，绝不连生产库
scripts/isolated_test.sh --keep -- .venv/bin/python -c "from lottery import auth; print('ok')"
T=<上一步打印的 /tmp/lott-isolated.XXXXXX>
mkdir -p $T/home
(PYTHONPATH=$PWD LOTT_HOME=$T/home LOTT_DB=$T/ssq.db \
 LOTT_BOOT_REFRESH_RULES=0 LOTT_COOKIE_NAME=ssq_sid LOTT_COOKIE_SECURE=0 \
 setsid .venv/bin/python -m lottery.cli serve --host 127.0.0.1 --port 18099 \
 > /tmp/coldstart.log 2>&1 &)
sleep 12

# ② 等 health 就绪后，计时「首次」请求（这是唯一有意义的那个数）
curl -s -o /dev/null -w "health=%{http_code}\n" http://127.0.0.1:18099/api/health
curl -s -o /dev/null -w "COLD time=%{time_total}s http=%{http_code}\n" \
  "http://127.0.0.1:18099/api/portfolio/popularity?reds=1,2,3,4,5,6"

# ③ 对照：热态（证明你区分了冷热）
curl -s -o /dev/null -w "WARM time=%{time_total}s\n" \
  "http://127.0.0.1:18099/api/portfolio/popularity?reds=1,2,3,4,5,6"

# ④ 清理
pkill -f "port 18099"
```

### 1.4 判定表

| 冷启动耗时 | 判定 | 处置 |
|---|---|---|
| `< 3s` | ✅ 通过 | — |
| `3s ~ 10s` | ⚠️ 阻断 | 报数，不许糊；需修 |
| `> 10s` | ❌ 阻断 | 必须修 |

**允许的例外（需显式申请）**：由用户**显式点击**触发的重操作（如「离线评估 30~120 秒」「全量回放 5 分钟」）。
这类操作本来就标注了预计耗时，不属「用户没预期就要等」。
**自动触发的**一律适用本门 —— 包括：进入某个 tab 就拉取的、首屏就发的、进子页就自动加载的。

### 1.5 我的测量记录（协议一致，可复算）

| # | 基准 | 冷启动 | 热态 | 判定 |
|---|---|---|---|---|
| 1 | `0f5656d` + 工作区 | **28.554343s** | 0.049952s | ❌ |
| 2 | `720c323`，严格按 §1.3 协议重跑 | **29.370946s** | 0.040321s | ❌ |

**两次相差 0.82s（2.9%），协议可复现** —— 这不是一次性抖动，是稳定缺陷。

**上限证明**：热态 `0.04s` 就是「模型已在内存」时的响应时间。
因此「启动预热 + 落盘缓存」修好后的可达目标是 **~0.04s**，与 3s 门限差两个量级 ——
**修法在原理上足够，不需要额外调优。**

进程内拆解（用于定位，不是替代端到端）：
```
load_draws()           0.12s
PopularityModel.fit()  6.92s   ← 主体
  _out_of_sample_check 7.08s   ← 滚动重拟合
  _ols(全量)           0.01s
```
**根因：在同步请求路径上跑训练。**

### 1.5b 本修复（popularity 预热+缓存）的三案验收协议

Lead 2026-10-21 指定，缺一不可：

| 案 | 场景 | 判据 | 说明 |
|---|---|---|---|
| **(a)** | 进程刚起、**预热未完成**时发请求 | **< 3s** | **最关键**。若 (a) 必须等预热完成才达标，等于把「冷启动 29s」换成「冷启动 + 排队」，没修 |
| (b) | 预热完成后请求 | ≈ 0.04s | 验证预热真的进了内存 |
| (c) | 落盘缓存**已存在**时重启后请求 | **< 3s** | 验证第 ② 项（落盘）真的生效，而不只是靠预热 |

**(a) 的用意**：预热是后台线程，用户可能在它跑完之前就来了。
若此时请求**也去抢锁并同步 fit**，用户仍要等 —— 只是从「等训练」变成「等锁 + 等训练」。
所以必须实测「预热未完成 + 用户来了」这个窗口。**这一案最容易做成假通过。**

### 1.6 已知会被本门抓住的场景清单（供他人自检）

- 模型 `fit()` 在请求内触发（本次案例）
- 首次请求触发惰性 import 重模块（numpy/scipy）
- 进 tab 就 `Promise.all` 并发拉 N 个重端点
- 首次渲染触发全量枚举（`ticket_distribution(exact=True)` n=10 约 0.1~0.2s，安全；n=100 需复测）

## 门 2｜验收人必须独立复跑

### 2.1 规则原文

> 验收人**必须自己重跑**被验收者的探针，**不许引用对方输出**。

### 2.2 两次实证（都是为了证明「报告为真 ≠ 结论成立」）

| # | 被验收者的报告 | 我复跑的结果 | 差异根因 |
|---|---|---|---|
| 1 | 齐交付：16 注 = 32 元、期望回收 16.73 元、回报率 15.625% | 16.73 是**全奖级**、15.625% 是**六等奖**，两者不能同屏 | 他的**口径**让缺陷不可见 |
| 2 | 刘工：39 条探针全绿 | **1 条失败** | 他的**热态缓存**让缺陷不可见（20s 超时 < 28.5s 实际耗时） |

**共同点：两次都不是说谎，是运行环境让缺陷不可见。**
这类问题的危险在于：**报告每一句都为真，但推不出「已通过」的结论。**

### 2.3 执行要求（三条硬约束）

1. **原件复跑**：跑被验收者给的那条命令本身，不自制「等价」命令。
2. **记录环境五件套**：冷/热、库状态、端口、**commit**、**`git status --short | wc -l` 的值**。
   缺任一项，结论不可复算。
   —— 第 5 项是 2026-10-21 我自己漏掉的一项：我记录了 `720c323`，但没记工作区有 11 个未提交改动，
   于是把「已提交版本未修复」写成了「修法未落地」。**commit 只说明你测了哪个提交，
   不说明你测的是不是那个提交的内容。**
3. **不许只跑一遍**：flaky 的方向常常正好掩盖缺陷（本次即如此）。**同一探针至少跑 2 次，其中至少 1 次必须是冷启动。**
4. **并发中间态不得下结论**：若目标文件正被他人重构（典型信号：公共函数暂时消失、
   `git status` 显示该文件为 M），此刻的测量结果**不具备判定资格**，只能记为观察。
   —— 判据：先 `import` 一下被测模块，公共 API 若缺失（如 `get_model` 不存在），
   说明正在重构，**停止测量**，等对方报「已落地」。

### 2.4 反例：我自己也犯过

我在同一轮里把「`lottery/engine.py` 已删除」当成持续事实（实际是事故期瞬时状态，几分钟后回滚）。
**我的错误和上面两次同族**：我的**观察时刻**让我的结论过期。
所以本门对验收人和交付人**对称适用**：
> 凡引用代码/运行状态，必须注明确切观察时刻；并发改动期间的工作区状态不得作为结论依据。

### 附-A 三案实测（工作区在途版本，**结论：a/a' 不合格**）

观察时刻 2026-10-21 14:04，工作区 15 个未提交改动，`popularity.py` mtime `13:59:55`。

| 案 | 场景 | 实测 | 判据 | 判定 |
|---|---|---|---|---|
| (a) | 单请求，预热在飞 | **25.41s**（200） | <3s | ❌ |
| (b) | 预热完成后 | **0.0088s** | ≈0.04s | ✅ |
| (c) | 落盘缓存存在时重启 | **0.133s**（prewarm 0.44s） | <3s | ✅ |
| (a') | 5 线程并发冷启动（进程内直测） | **fit 执行 1 次 ✅ / 5 线程各等 18.44s ❌** | 全部<3s 且 fit 仅 1 次 | ❌ |

**核心结论：锁把「重复 fit」解决了，但没解决「用户等训练」。**
并发 5 个线程全部阻塞在同一把锁上等那一次 fit（18.44s），
即我在 §1.5b 预言的失败形态 —— **从「等训练」变成「等锁 + 等训练」**。

**根因**：`get_model()` 在锁内同步 `fit`，请求没有「锁获取超时 → 返回未拟合对象」的
降级路径。两种设计取舍：

| 设计 | 用户看到 | 代价 |
|---|---|---|
| 阻塞（现状） | 等 18s，然后 200 | 首屏卡转圈 18s |
| **降级（建议）** | ~0.05s 得到 503 / 未就绪，前端显示「模型拟合中」 | 需要一次重试 |

**Lead 的 (a) 判据（<3s）只有在降级设计下才可能成立** —— 所以 (a) 不合格不是「预热没做好」，
而是「缺降级路径」。(b)(c) 好看不能替代 (a)。

**另一条独立问题：预热本身耗时 26~38s**
```
一次实测 [warmup] 大众偏好度模型已就绪: 26.09s
另一次                                : 38.55s
进程内单次 fit                        : 18.4s
```
即使请求**不阻塞**，服务启动后前 20~40 秒内到达的用户仍拿不到模型。
**所以单靠预热不够，必须配合 (a) 的降级路径。**

### 附-A2 降级设计裁决后：已落地部分 + 两处待补（观察时刻 14:06，load average 15.60）

**待补 ②：503 文案在降级场景下是误导（产品口径问题）**

| 真实原因 | 用户该做什么 | 现有文案的暗示 |
|---|---|---|
| 数据不足（`n_train < 300`） | 等更多期开奖，短期无解 | 「数据不足」✅ 对 |
| **正在拟合（预热中，约 5~20s）** | **等 5 秒刷新即可** | 「数据不足」❌ **让用户以为功能坏了** |

建议按 `reason` 分叉：

```json

{"ok": false, "reason": "insufficient_data", "retry_after": null,

```

前端 `_degradeNote` 已能显示任意 error 文案，**不需要新增 UI**。

### 附-F 门 2 第 5 条：先验测量，再报缺陷（Lead 批准）

> **测量结果与代码事实矛盾时，先验测量再报缺陷。**
> 判别顺序：
> ① 环境变量是否真的传到了（**`VAR=x cmd` 对 shell 函数不导出**）
> ② 是否测的是你以为的那个进程 / 端口 / commit
> ③ 才怀疑代码。

**实证（2026-10-21，我自己）**：测 `LOTT_POPULARITY_WARMUP=0` 的 C 案得 `200 / 27.1s`，
与「请求路径永不自 fit」的代码事实矛盾 → 按 ①②③ 排查，发现是 `VAR=0 some_function`
未导出给子进程，服务端收到默认值；改 `export` 后为 `503 / 2.56s`，与代码一致。

**为什么这条重要**：**假警报的代价与假通过同级** ——
假通过让缺陷溜走；假警报让对方白忙、且会损耗「异常数字」这个信号的可信度（狼来了）。
一旦团队习惯「报异常前不验测量」，真异常也会被当成噪声。

**与本门其他条款的关系**：门 2 第 2 条（环境五件套）防的是**记录不全**；
第 5 条防的是**解释错位** —— 记录齐了，但把测量工具的缺陷算到了被测对象头上。

### 附-G A1 判据必须是「双判据」（Lead 采纳）

原 A1 判据只有延迟，现补语义：

```python
# A1：无缓存·首个请求（预热在飞）
assert r.status_code == 503
assert r.time_total < 3.5                       # ① 延迟门
assert body["reason"] == "model_warming"        # ② 语义门
```

**延迟照样 2.4s 达标**，但用户会以为功能坏了（「数据不足」= 短期无解，
「正在拟合」= 刷新即可）。**延迟门管不住文案门** —— 两者是独立的门。

### 附-J 新发现（P2）：`retry_after: 5` 是一个偏短的假承诺

**用户实际体验**：照提示 5 秒后刷新 → 仍 503 → 再刷新还是 503（预热要到 20~40s），

2. 零风险：`retry_after: null` + 「稍后刷新」（诚实但丢掉提示价值）；
3. 正确解（新能力）：预热线程记录「上次预热耗时」，据此动态给值 —— **需 Lead 立项**。

**建议 1 先用（一行常量改动 + 一句文案），把 3 作为后续优化。**
判定：**P2**（不阻塞发布，但会让披露失信）。

### 附-K `retry_after` 裁决（Lead：方案 1，常量 30）+ 三组测量校正

**先更正我引用过的「fit≈6s」**：三组独立测量差异主要来自负载，不是代码。

| 测者 | fit 耗时 | 环境 |
|---|---|---|
| 我 | 6.06s | load 15.6 |
| Lead（容器内 ×2） | 10.27s / 10.36s | load 13.09 |
| 李工 | 12.64s（争 CPU 时 40s+） | load 4.2 |
| 我（预热整体） | 26.09s / 38.55s | 上界 |

→ **真实成本应表述为「6~13s，随负载浮动，极端可达 40s」，不是「≈6s」。**
（这三组中「load 越高耗时越低」的反常，说明还有 CPU 配额/缓存命中差异，**不应用来推因果**。）

**裁决**：`_POPULARITY_RETRY_AFTER_SECONDS = 30`
- 30 落在「常态上界之上、极端之下」：用户照 30 秒刷新，中位情况一定好了；极端情况再刷一次；
- 20 不够（实测到 38.55s）。

**配套文案**：`"模型未就绪：正在拟合（通常 10~30 秒），稍后刷新即可"`

⚠️ **实现坑（我已告知李工）**：现有代码用 `"约 %d 秒后自动可用" % retry_after`。
若只改常量不改格式串，文案会渲成「约 **30** 秒后自动可用」——
**等于把点值又写死一遍，白改。** 正确做法：**文案给区间（给人），`retry_after` 只走字段与 HTTP 头（给机器）。**

### 附-L 新增：`retry_after` 必须可证伪（Lead 要求，我补的实现口径）

只把常量从 5 改成 30，只是「把错的数换成另一个数」——**仍然没有人验证它是否兑现**。
所以加一条**比例断言**：

```python
measured = <上次预热耗时 或 隔离库实测一次 fit>
assert retry_after >= 1.0 * measured   # 承诺不能比实际短（用户照做会落空）
assert retry_after <= 4.0 * measured   # 承诺不能远大于实际（用户白等 / 防写死 300）
```

**为什么用比例不用绝对值**：fit 在 6~40s 间浮动，写死 `== 30` 会在慢机「通过但无意义」、
在快机「无谓失败」。比例让两个量同步变化。

**实现建议**：预热线程记 `_LAST_WARMUP_SECONDS`，测试读它 ——
顺带对上李工本来就要改的那处（30s×10 重试）。

**必须在 docstring 写清**：测的是**一致性**（承诺与近期实际同量级），不是**准确性**。
否则下一个人会把它当精确断言，在负载波动时误判为回归。

### 附-O 门 1 增补：判据设计错误的识别

刘工的「探针跑完后仓库 `data/popularity_model.json` 存在性不变」每次都红 ——
根因：`ssq-predictor` 容器把仓库 `data/` 挂到 `/app/data`，**容器自己的预热线程会随时写它**。
→ **`exists()` 前后对比这个判据本身是错的**，它无法区分「谁写的」。

**规则**：判据必须能**归因到被测对象**。
无法归因的判据（只看「有没有变」，不看「谁改的」）在多主体共享资源上必然出错。
→ 修正方式不是「加 sleep 等它稳定」，而是**把「所有人」纳入判据**（只看自己的 `LOTT_HOME`、排除仓库路径）。

### 附-P 契约：`reason` 不得比它旁边的字段更粗（P2，已派李工）

现状：
```json
{"reason": "model_not_ready", "unfitted_reason": "warming_disabled", "retry_after": null}
```
**主字段（`reason`）比副字段（`unfitted_reason`）更粗** ⇒ 只读 `reason` 的第三方调用方**必然分叉错**。

**同族**：与 D-07「一个 usable 两个意思」同类 —— 不是数值错，是**分层错位**，
使读者无法仅凭主字段判断该做什么。

**规则**：**API 的主字段必须自解释**。若需要第二个字段才能正确分叉，说明主字段设计错了。
兼容别名可以有，但**方向必须是「主字段细分、别名兜底」**，不能反过来。

### 附-Q 前端 `_degradeNote` 的 bug 形态（可推广）

```javascript
const reason = pl.reason || pl.unfitted_reason;   // ❌ 粗分类有值时，细分永远读不到
```
**`||` 表达「前者缺失时用后者」，用于「粗/细两级并存」的字段是错的。**

**规则**：凡「两级字段并存」，不许用 `||` 读，必须：
```javascript
const reasons = [pl.reason, pl.unfitted_reason].filter(Boolean);
```

### 附-E 新发现：`model_not_ready` 的文案在「预热关闭」配置下不成立

C 案（`LOTT_POPULARITY_WARMUP=0` + 无缓存）返回：
```json
{"ok":false,"reason":"model_not_ready","unfitted_reason":"unknown","retry_after":5,
 "error":"模型未就绪（拟合未完成或失败），稍候会自动重试"}
```

**「稍候会自动重试」在这一配置下是假的。** 依据：重试循环在 `api_app.py:530`
（`for attempt in range(1, _MAX_ATTEMPTS+1)`），而它位于 `_popularity_warmup()` 内部，
该函数整体被 `api_app.py:566` 的 `LOTT_POPULARITY_WARMUP != "0"` 门控。
→ 预热关闭时：后台无人 fit、请求路径不自 fit ⇒ **模型永不就绪，卡片永久不可用**，
而文案承诺「会自动重试」，用户会一直等一个不会发生的事。

**修法建议**（属产品口径 + 后端小改）：该配置下改用独立 reason 与文案，例如
```json
{"ok":false,"reason":"warmup_disabled","retry_after":null,
 "error":"大众偏好模型未启用（部署配置关闭了后台预热），本卡在当前部署下不可用"}
```
**`retry_after` 必须置 null** —— 告诉前端「别等了」，而不是给一个假的 5 秒。

严重度：**P3**（非默认配置，默认开启），但属于「文案承诺了不会发生的事」，性质与本次审计主体一致。
