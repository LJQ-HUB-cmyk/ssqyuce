## 零、一句话总裁决

**四个方向全部具备改造条件，没有一条需要推翻；但 5 处表述必须改写才算"可落地"，其中 1 条（"只要能套上就纳入"）按原话执行必然把系统变成噪声库。**

最关键的一条新发现不在方案里，而在代码里：**「验证规律」这一环在生产上根本没有写入者**——`register_prereg` 全仓零调用，导致 33 条假说的 `prereg_status` 全是 `None`，`usable_rules()` 结构上恒为空。**即使用户现在把 `LOTT_RULE_APPLY` 打开也毫无作用。** 这是"挖/验/用"三段分离真正的第一块砖，必须在任何挖掘功能之前修好。

## 三、必须纠偏的 5 处表述（可直接替换用户原文）

### C1. "整个系统模块化，防止一个崩溃影响系统"

**错在哪**：单容器单进程里，进程崩 = 整站挂（`restart` 拉起约 2 分钟窗口）。"零影响"物理上不存在。用户要的其实不是微服务。

**改写**：
> 目标是**功能级降级 + 进程级自愈**：任一功能模块（挖掘/验证/出号/AI/通知）超时或异常时，同请求其余卡片正常返回并显示明确原因；进程级崩溃仍会导致约 2 分钟不可用，由 `restart` + 健康检查覆盖。**验收方式**：每个模块上线须附一条"杀死该模块后其余端点仍 200"的测试。**不采用**微服务/sidecar（768MiB 内存放不下第二个 Python 进程）。

### C2. "只要能套上用于预测的都可以纳入（扩大规律库）"

**错在哪**：与"验证规律"逻辑互斥。纳入标准越松，验证闸门的假阳性负载越重；叠加闲时全天候挖掘，候选洪水会把 FWER 推向 1。

**改写**：
> **扩大的是"候选池"，不是"可用集"。** 任何想法都可登记为候选（登记≠可用），且登记必须带机器可读的规格；候选进入"可用"必须过三道闸：① 前置注册并到期判定（`prereg_ok=True`）；② 统一误差预算（累计口径，α 只花一次）；③ 失效判据（连续 K 期不达标自动退居 monitor）。**未过闸者只进"观察区"，永不进出号通道。** 注册速率上限 10 条/期。

### C3. "尽可能发挥大模型在每个位置的作用"

**错在哪**：与可测性冲突。V10 已证明三个"发挥"实为表演（出号 = 死锁；给自家候选排序 = 猜规则；abstain 引用 = 抄写题）。且当前系统反而让 LLM 拿到**非能力来源的优势**（+20 偏置），这既污染评估也不符合用户真意。

**改写**：
> 大模型进入**有机器金标准的岗位**（输出 schema 固定、金标准由确定性代码唯一确定、可 0 误差判分）：结果叙述、契约检查、验证方案设计、维度提案、意图解析、票单目标选择。**"不做"清单与"做"清单同等重要**：出号候选、状态降级动作、显著性判定三处永不交给 LLM。**LLM 全挂时系统必须照常出号**（纯统计通道），降级路径随岗位一起上线。

### C4. "不要强调彩票的独立性和随机性、不可预测性"

**错在哪**："不强调"若滑向"不检验"，等于授权自欺；且对用户不诚实（负期望是事实）。

**改写**（三段式，可直接用于 UI）：
> ① 本系统是**娱乐软件 / AI 验证实验**，不承诺任何中奖收益（期望为负，见组合期望值卡）。
> ② 我们不拿"随机不可预测"当结论，但拿它当**对照组**：每条规律都要回答"比均匀基线强多少（lift）、强多久、何时失效"。
> ③ 当前可用规律数 N（实测 **0**，另有 17 条在观察区）——**先展示 N，再讲故事**。

**关键区分**：**"不强调随机性"约束的是叙事语气，不约束误差预算。** 统计卫生是对"程序"的要求（当数据无信号时，系统声称"已验证"的条数应受控），与"世界是否有规律"无关——因此这个定位下依然可以、也必须做严格检验。

### C5. "系统不进行预测时自动利用闲置资源挖掘规律"

**错在哪**："闲置资源"在本机不成立（实测：容器余量 376MiB、15 个邻居容器、宿主 4 核已用 7GB）。

**改写**：
> 挖掘任务仅在**四条件同时满足**时运行：① 过去 30 分钟无在线预测请求且非开奖窗口；② 容器内存 < 70% 且宿主 `load1 < 2.0`；③ 当日 LLM token 预算有余额；④ 无其它后台任务在跑。在线请求到达后 **5 秒内让路**，任务可**断点续跑**。配额写进配置并暴露到 `/api/health`，**超配额运行视为事故**。

## 四、本轮最关键的 8 条实证发现（Lead 独立验证）

### 4.1 【已确认失败】真值锁测试失败 —— 跨模块时序耦合的活标本

`pytest -q` 实跑 **1 个失败**：`tests/test_v12_shape_lock.py::test_production_pass_rate_is_locked_on_real_data`
栈：`lottery/engine.py:41` `np.percentile(s, 5)` → `IndexError: index -1 is out of bounds for axis 0 with size 0`

**根因链（三段生命周期彼此脱钩）**：
1. `tests/conftest.py` 的 autouse fixture 把**所有**用例 `config.DB_PATH` 重定向到临时空库（这是 V10-00b 为修"字母序巧合全绿"加的正确隔离）；
2. 该用例守卫 `_has_real_db()` 在**收集期**求值，那时 conftest 尚未 patch → 读到真实库 3516 期 → 判定 True、**不 skip**；
3. 用例执行时 conftest 已生效 → `load_draws()` 返回 `[]`；
4. `constraint_ctx([])` 对空数组调 `np.percentile` → 抛穿。

**为什么这是第 1 点的标本**：同一个"是否有数据"的问题被两个模块用两套时序回答，下游对空输入**零防御**。
**修法（两条，都很便宜，合计 <50 行）**：① 守卫改为执行期求值；② `constraint_ctx` 对空/短输入返回明确降级值或抛**类型化异常**（`InsufficientDataError`），不让 `IndexError` 抛穿。

**范围确认（r1 实测，好消息）**：全仓扫描"空/短输入未设防"的地方，**只有 `engine.constraint_ctx` 一处会崩**——`features.py` 与 `shape_rules.py` 已有逐项守卫（属正例）。**所以这一类风险是"点修"而非"面改"，成本远低于预期。**

### 4.2 【本轮最重要】「验证规律」在生产上没有写入者 —— 三段分离的第一块砖

- `grep -rn "register_prereg"` → **`lottery/` 下零调用**，仅 `tests/` 13 处。
- 生产 `data/hypotheses.json` 33 条：`prereg_status` **33/33 = None**、`prereg_ok` 33/33 = None、`batch_id` 33/33 = None、`n_tested_cumulative` = 0。
- 链路：`patterns_runtime.py:125` 要求 `prereg_ok is True`（不可绕过）→ `prereg_ok` 只能由 `evaluate_prereg()` 写 → 它只处理 `prereg_status ∈ {registered,...}` → 只有 `register_prereg()` 能写该字段 → **而它没人调用**。
- ⇒ **`usable_rules()` 结构上恒返回 `[]`** ⇒ `engine.apply_rules_to_candidates` 恒走 `mode="off"`。

**所以：把 `LOTT_RULE_APPLY` 从 0 改成 1 完全无效。** 这是"挖/验/用"断链的最上游，**必须先修，再谈闲时挖掘**（否则是往没有出口的水池灌水）。最小修复约 **3 行**：在 `api_app.py:2190` 快照刷新前，把 `discover()` 候选作为一批调 `register_prereg`。

### 4.3 历史上"扩大定义"的尝试从未真正运行

`mining.run_mining` **只在 `cli.py:100` 被调用**，API 与调度器从不触发 ⇒ `mining_runs` 0 行、`mining_artifact.json` 自 2026-10-05 未更新。这印证前序裁决的判断：**用户要求扩大定义 → 系统加了族 → 族从未真跑 → 系统继续报"没有规律"**。

### 4.4 扩大定义确有真实空间：`order` / `sales` / `pool` 存在但零使用

`parser.py` 已解析全部 31 字段：`order`（摇奖顺序 o1–o6）、`sales`（销量）、`pool`（奖池）、`prizes`（奖级）。
DB 实测有值（2026119：sales=364,378,528、pool=1,025,112,736）。
但 `order` **全仓 0 处读取**，`sales`/`pool` 从未进入任何规律族。
⇒ 这是"扩大假设空间"**现成的、零数据成本的**两个方向（第二数据轴 + 位置维度），比再造判别式更有价值。

### 4.5 三段分离的真实障碍是 8 组循环依赖，且恰好跨在找/验/用边界上

AST 解析 37 模块：`engine↔evaluate`、`evolution↔hypothesis`、`patterns_runtime↔rule_lifecycle`、`evaluate↔replay` 等 **8 组双向环**。
且多处用**函数体内延迟导入**打补丁（如 `engine.py:556`、`evaluate` 内 `from . import replay`）——这意味着失败会**推迟到请求时**才暴露，正是崩溃传播的路径。
⇒ 用户要的"三段分开"在代码里是**方向正确但被咬合**，改造重点是**解环 + 画接口**，不是新造架构。

### 4.6 单全局 SQLite 连接：无锁、无 WAL、无 busy_timeout

`db.py:167` `sqlite3.connect(..., check_same_thread=False)`，单个全局 `_CONN`，**无 `Lock`、无 `timeout=`、无 `journal_mode=WAL`**。
配合 **79/80 同步端点共享 40 线程池** + 6 个 daemon 线程（含每 1800s 一轮的调度器）：一次长写事务即可让全站读写阻塞并在 5 秒后抛 `database is locked`。
**这是第 1 点最便宜、最硬的一刀**：加 `WAL + busy_timeout=5000` 两行，不碰任何业务逻辑。

### 4.7 生产 80 个端点全部匿名可访问

`docker-compose.yml:21` `LOTT_TOKEN=${LOTT_TOKEN:-}`，`.env` **未设** `LOTT_TOKEN`；`api_app.py:37` 的 `_optional_api_auth` 在 token 为空时直接放行。
⇒ 任何知道 `https://ssq.ff88.de` 的人可调 `/api/predict`、`/api/evolution/run`、`/api/llm_lab/run` 等**会烧 LLM 费用、会写库**的端点。这是安全底线问题，应与改造同批修。

### 4.8 V11 严格模式正在破坏"LLM 到底行不行"的可测性

`.env` `LOTT_STRICT_MODE=1`；`engine.py:2438` 对 `llm:` 通道用 `conf = 20 + 0.45*(...)`，统计通道用 `conf = 10 + 0.25*(...)` ⇒ **LLM 恒定 +20 起跑优势**。
后果：最近 5 期 25 注中 **24 注由 LLM 决定**；而 `battle.llm_arm_report` 要求"同期两臂注数相等"，同期只剩 llm 行 ⇒ **永久 `n_pairs=0`**。
⇒ 用户第 4 点要"发挥大模型"，但当前配置让 LLM 靠偏置胜出、且**永远无法被评估**。这是必须先拆掉的。

## 五、改造蓝图

### 5.1 七层边界（不是拆进程，是画清"谁慢/谁快/谁写库/谁调 LLM"）

| 层 | 职责 | 现状文件 | 隔离要求 |
|---|---|---|---|
| 1 数据面 | 唯一写 DB 的地方 | `db.py` | 补 WAL / busy_timeout / 写入口收敛 |
| 2 规律挖掘 | 生成候选（宽） | `discovery.py` `mining.py` `multiscale.py` `regime.py` | 配额 + 可中断 + 让路 |
| 3 规律验证 | 判定候选（严） | `hypothesis.py` `rule_lifecycle.py` `rigor.py` | **必须补写入者**（§4.2） |
| 4 规律使用 | 出号（受控） | `engine.apply_rules_to_candidates` | shadow 默认，转 active 需对照证据 |
| 5 AI 网关 | 唯一对外 HTTP | `llm_client.py` | 超时/重试/降级/预算（已有基础） |

| 7 视图 | 参数→调用→JSON | `api_app.py`(3381行) | 瘦身；"安全路径"白名单独立线程池 |

### 5.2 隔离机制选型（结合本机现实）

| 方案 | 可行性 | 结论 |
|---|---|---|
| ① 进程内 try/except + 超时 | ✅ 低成本 | **先做**（已有基础） |
| ② 线程池分层 + 独立探活 | ✅ 内存 +0 | **推荐**（防 `/api/health` 被饿死） |
| ③ 多进程 / 多 uvicorn worker | ⚠️ 每进程 +200~300MiB，余量仅 376MiB | **不推荐** |
| ④ 独立容器 / sidecar | ❌ 15 容器已在挤，且不解决本项目问题 | **否决** |
| ⑤ `restart` 自愈 | ✅ 已具备 | 保底 |

**推荐 = ① + ② + ⑤**。

### 5.3 统一 Rule Protocol（第 3 点落点，约 200 行新文件 + 3 人日迁移）

必须字段：`假设空间` / `适用条件` / `打分器` / `显著性判据` / `失效判据` / `使用方式`，外加 `layer`（L1/L2/L3，**禁止相加**）与 `replayable`。
**核心纪律**：新增一族规律只允许改注册表一行；"扩大定义"= 扩大**候选池**，可用集仍受闸门约束。

## 六、路线图与工期

### 6.1 依赖顺序（不是并列，任何跳步都会复刻 V10 的坑）

```
P0 Gate 收尾 → P1 精简 → P2 模块化 → P3 挖/验/用分离 → P4 闲时挖掘 → P5 LLM 岗位 → P6 总验收
```

- **精简必须在模块化之前**：给要删的代码写接口是纯浪费，且精简后的边界才是模块边界。
- **分离必须在模块化之后**：`register_prereg` 的调用点本身就是模块边界。
- **闲时挖掘必须在分离之后**：无验证闸门的挖掘 = 噪声生产机。
- **LLM 岗位最后**：每个岗位都要消费前面产出的契约与判分器。

## 十、诚实边界（对用户第 6 点的正面回答）

1. **本系统不会、也做不到提高中奖概率。** 单注 EV 由组合恒等式钉死（`E[K]=12/11`），与选号策略无关。
2. **但"不强调随机性"不等于"放弃检验"。** 本方案的定位是：**娱乐软件 + AI 可验证性实验**。它承诺的不是"能找到提高中奖率的规律"，而是——
   > **本系统声称"已验证"的每一条规律，在其自身声明的错误率下都经得起复核，且这个错误率可见、可审计、不随挖掘次数膨胀。**
3. **这个承诺恰恰是差异化价值**：市面上没有彩票软件能说清"我这 5 条规律凭什么出现在首页"。本系统的答案是：每条规律自带一个 e-value 与一份被花掉的 α 额度，且总额封顶。
4. **当前可检出效应下限是 +5.88%**（n=3516 的信息量上限）。任何多重检验技巧只能提高召回，不能降低这个下限。
5. **"修好后仍然找不到"与"现在找不到"的可信度完全不同**——目前 `usable=0` 与"判据写死/写入者缺失"无法区分。改造的价值首先是把"找不到"这个结论变得可信。
