### 1.3 必须单列的一处：`web/index.html:332` 把恒等约束称为"可用规律"

前端原文（用户可见）：

> 这些**不是**「预测下一期」的规律，而是**组合数学恒等约束**：
> 任何一期开奖的形态（和值/跨度/三区/奇偶/连号）都几乎必然落在这些区间内
> （实测 3515 期与 C(33,6) 全空间理论枚举一致）。
> **作为严格模式的「可用规律」，LLM 在此约束下生成的注单，形态必然合理。**

**准确判定（经 Lead 复核后修订，不夸大也不轻描淡写）**：

一句"几乎必然落在这些区间内"已经自我否定了它的"规律"属性——**恒成立的东西没有信息量**。却在同一段里又挂上「可用规律」的标签，这是**术语上的自相矛盾**。

**但必须同时说明**：这句话的**上半句**已经用「**不是**「预测下一期」的规律，而是组合数学恒等约束」明确否定了预测含义，读者不会被误导成"这就是预测规律"。因此这是**术语纪律违规，不是误导性造假**。

**后端自己的纪律恰恰相反**（`lottery/routes_predict.py:100-110`，原文）：

> 口径纪律（V12-04 强制）：这门控只能命名为 **layer=="L2" 且 violation=0**，
> **不得**把它叫成「可用规律」——L1 的「可用规律」语义是「检出/未检出」，
> 与 L2 的「约束满足率」不是同一种计数，混用正是「可用规律 0 vs 5 条」矛盾的来源。

**即：后端工程师写下了"不得叫可用规律"的强制注释，前端文案误用了这个禁用词。** 这不是统计问题，是**术语层脱离了代码约束**——修复成本极低（**改 1 行**：`可用规律` → `结构门控条件`），但它是用户产生"被糊弄感"的诱因之一。

### 关于 ①「可用规律」的准确判定（不夸大也不轻描淡写）

**既不能升格为"造假"，也不该被当作无害**：

- ✅ **成立**：最后半句确实使用了后端明令禁用的词，且与前文「**不是**预测规律」自相矛盾；
- ✅ **但**：该句紧接在明确的「不是…而是…」否定句之后（`index.html:329`），**读者不会被误导成"这就是预测规律"**；
- ✅ **因此**：这是**术语纪律问题，不是误导性造假**。1 行可修。

> 修订理由：我最初把它列为 🔴「明确误导」是**过重的**。在用户明令"不能造假"的语境下，把措辞违规说成造假，会让用户对整份评估失去信任——**这本身也是一种不诚实**。

### 口径冲突专节：两个 "usable" 是两件完全不同的事

这是我发现的、比术语问题更实质的风险。**同一系统里 "usable" 一词被用于两个互不相干的语义**：

| | `patterns_runtime.json` | `idle_mining_state.json` |
|---|---|---|
| 字段 | `counts.usable` = **0** | `by_decision.usable` = **20**；顶层 `usable` 字段 = **`{}`（空）** |
| 语义 | **生产快照中、通过阶段持续有效 + A/B 验证 + 前置注册的可用规律** | **单候选 e-value 越过 1/α 阈值的计数**（`threshold=20.0`, `alpha_spent=0.05`），**未做族级校正** |
| 用途 | 决定是否允许出号（严格模式门控读取 `usable_replayable`） | 闲时挖掘的**中间筛子**，从不参与出号 |

**本次实测核对**：`candidates` 共 **20** 条，`decision` 全部为 `usable`（不是 19；Lead 复核为 19，差异可能来自读取时点）。顶层 `usable` 字段为 `{}` 空字典——**同一文件内 `usable` 已是两种东西**。

**🔴 并且这 20 条本身也不构成任何证据**（此点比 Lead 所述更进一步）：

```
by_decision: monitor 21780 + usable 20 = 累计测试 21800 次
每候选阈值: e-value > 1/α = 20
纯随机（全局 H0）下越阈条数的期望上界 = 21800 / 20 = 1090 条
实测越阈 = 20 条  → 远低于纯随机期望
```

**即：即便按它自己的单候选口径，20 条也低于"纯随机就该出现"的数量级。** 这个数字不但不能证明有规律，它的**稀缺性本身反而是"没有信号"的证据**。

**结论**：`usable=20` 与 `usable=0` 不是"两个版本的说法"，而是**两个不同统计量共用了一个词**。若在 UI 上并列展示，用户看到的将是"系统说有 20 条可用规律，又说 0 条可用"——**这会直接摧毁用户对全部数字的信任，哪怕每个数字单独看都对。** 这是必须优先修的**命名问题**。

### 一句话总结

用户说"造假"，指的很可能**不是**系统伪造了数据（系统没伪造），而是**系统在"预测"这个已被自己证伪的招牌下，持续展示带"规律""可用""命中率"字样的东西，且这些词在不同地方含义不一致**。这是**命名与术语问题，不是数学问题**——也正因如此，它是**两周内能修好的问题**。

## Q2 「有益」的可执行定义

### V1. 「至少中一个蓝球」的覆盖率提升 — ✅ 已实现，数学严格成立

**依据**：`lottery/engine.py:1110-1160`（`blue_coverage_plan` docstring 完整推导）

```
随机重复（可重复抽样）：P = 1 - (15/16)^n
去重覆盖（本函数）    ：P = min(n, 16) / 16
n=10: 47.55% → 62.50%（+31.4% 相对提升）
n=16: 64.39% → 100.00%
```

这是**纯组合数学恒等式**，不依赖任何预测能力。代码注释自己写下了边界：「六等奖期望返奖比恒为 0.156，与 n 无关」——即覆盖改变**中奖频率**，不改变**期望值**。**这条是系统最大且最被浪费的资产。**

**缺口**：前端只在 `app.js:2430` 一处小字显示 `P(≥1 蓝) 覆盖 x/16`，且藏在"票单分布"卡里。**主路径（生成预测后）完全不展示"你这 10 注把中蓝球概率从 47.6% 提到了 62.5%"。**

## 「避开热门形态」的真实价值与诚实边界

> 本节结论经**独立复算**，与 Lead 的探针结果逐项比对。数据来源：`data/ssq.db`，`SELECT p1, p1_amt FROM draws WHERE p1>0 AND p1_amt>0`，n=3266（另 251 期 `p1=0` 无人中头奖，无金额，单独说明）。

### 1. 效应是真是假：真（独立复现成功）

先标准化 `norm = p1 / (sales/1e8)`（销量是 p1 的最强驱动，`rho(sales,p1)=+0.4666`，不标准化会得出假结论）。标准化后 Spearman 相关（n=3428）：

| 形态特征 | 我的复算 rho | p | Lead 的 rho | 一致性 |
|---|---|---|---|---|
| 连号数 | +0.0127 | 0.456 | +0.0127 | ✅ 完全一致 |
| 同尾数 | +0.0759 | 8.4e-06 | +0.0759 | ✅ 完全一致 |
| 极差 | −0.0263 | 0.124 | −0.0263 | ✅ 完全一致 |
| **≤31 的个数**（生日号） | **+0.1389** | **2.2e-16** | +0.1389 | ✅ 完全一致 |
| 和值 | −0.1189 | 2.4e-12 | −0.1189 | ✅ 完全一致 |

混杂排除亦复现：`rho(≤31个数, 和值) = −0.4168`（同一效应的正反表述，**不是一个独立发现**）；分层固定后仍有净效应：

```
small=4: n=106  rho(sum,norm) = -0.1792 (p=0.063)
small=5: n=995  rho(sum,norm) = -0.0988 (p=0.0018)
small=6: n=2327 rho(sum,norm) = -0.0473 (p=0.0223)
```

**结论成立**：号码越"生日化"（6 个红球全在 1–31），同等销量下头奖中奖人数越多。机制清晰——**大量彩民按生日/小号选号**。

### 2. 形态能压低多少 p1：约 22%

```
small=6（全≤31）: n=2327  归一化 p1 均值 = 2.9619
small=5         : n=995   归一化 p1 均值 = 2.3016
→ 避开"全小号"可让 p1 下降约 22.3%
```

### 3. 从 p1 到金额：单注金额与 p1 的**非单调**关系（Lead 表已复现）

| p1 分段 | n | 单注金额均值 | 单注金额中位 | 封顶率(≥1000万) |
|---|---|---|---|---|
| 1 | 252 | 680 万 | **500 万** ← 保底 | 31.7% |
| 2 | 310 | 765 万 | 750 万 | 47.4% |
| 3 | 316 | 823 万 | 1000 万 | 52.5% |
| 4 | 313 | **841 万** | 922 万 | 31.9% |
| 5 | 310 | 811 万 | 848 万 | 9.0% |
| 6 | 262 | 783 万 | 808 万 | 1.9% |
| 7–8 | 423 | 720 万 | 736 万 | 1.4% |
| 9–12 | 468 | 655 万 | 663 万 | 0.4% |
| 13–20 | 391 | 593 万 | 598 万 | 0.3% |
| 21–40 | 165 | 536 万 | 550 万 | 0.0% |
| 41–200 | 56 | **476 万** | 517 万 | 0.0% |

**非单调性的成因（已核实）**：单注金额 = 当期一等奖总奖金 ÷ 中奖注数。总奖金池随销量增长而 p1 随"受欢迎度"增长，两条曲线**同向**，故：

- `p1=1` 时金额受**保底 500 万**托底（中位恰为 500 万），而不是最高；
- `p1=4~5` 时总奖金已增长、除数仍小 ⇒ **单注金额峰值 826~841 万**；
- `p1≥41` 时摊薄至 476 万。

**因此绝不能写成"越冷越好"。** `p1=1` 的 680 万 < `p1=4~5` 的 841 万，这是保底截断造成的，不是规律。

### 4. 金额对 p1 的真实弹性 —— 🚫 一个已证伪的乐观数字，不得用于决策

> **【作废声明】** 曾有一个广为流传的估算：「极端热门(p1≥21) 均值 5,212,219 vs 常态(4≤p1≤10) 7,636,006，差 **+46.5%**」。
> **该数字在算术上复现无误，但在因果上作废。** 它是**两组不同奖池规模的期次之间的对比**，把「奖池规模差异」误读成了「避开热门的收益」。
> **任何人不得再用 +46.5%（或据此推出的 0.14~0.18 元/注）作为本项收益的依据。** 下文给出证伪过程。

两项独立检验：

**(a) 组间差被奖池混淆。** 在**未封顶**样本（n=2731）上：

```
rho(p1, amt)   = -0.03 (本次) / -0.26 (Lead 复算)   ← 方向一致，量级有分歧，但都远弱于组均值暗示的强负相关
rho(pool, amt) = +0.56 (本次) / +0.50 (Lead 复算)   ← 两次独立计算一致：奖池才是金额主因
```

**(b) 弹性远弱于 -1 —— 这一项是决定性的。** 拟合 `log(amt) = a + b·log(p1)`：

```
本次:  b = -0.1533  (p1≥2, n=3014, R²=0.197)
Lead:  b = -0.0881
纯盈亏分等式 amt = pool/p1 的理论上限:  b = -1.00
```

两次独立计算都给出 **b 远离 −1**（−0.09 ~ −0.15，相差约 1.7 倍，但对结论无影响）。原因：**高 p1 的期次同时是高销量、高奖池的期次，两个效应几乎完全抵消。**

按实测弹性，`p1` 下降 20% → 单注金额只涨 **约 2%~3.5%**，而非纯恒等式的 **+25%**。

**为什么 +46.5% 必须作废（一句话）**：它假设"把号码从热门组换到常态组"能让 p1 从 21 掉到 7；但 `rho(形态, p1) = 0.139` 意味着形态只解释 p1 方差的 **≈1.9%**。**形态几乎无法可靠控制 p1**，所以那个组间差是不可达的。

### 5. 换算成期望收益：0.005 ~ 0.18 元/注（区间，非点估计）

中头奖概率恒为 `1/17,721,088`（**与选号完全无关**），头奖金额中位 684 万。

| 口径 | Δ金额 | **期望增益** | 占 2 元成本 | 状态 |
|---|---|---|---|---|
| ~~组均值差 +46.5%~~ | ~~318 万~~ | ~~0.180 元/注~~ | ~~9.0%~~ | 🚫 **已证伪（混杂对比）** |
| 恒等式上界（须能任意控 p1）| 171 万 | 0.097 元/注 | 4.8% | ⚠️ 理论值，**形态不可达** |
| 实测弹性（Lead, b=−0.088）| 约 9 万 | 0.005 元/注 | 0.3% | ✅ 可信下界 |
| 实测弹性（本次, b=−0.153）| 约 14 万 | 0.008 元/注 | 0.4% | ✅ 可信下界 |

**对外统一采用区间口径：`0.005 ~ 0.18 元/注`（占成本 **0.3% ~ 9%**）**，并必须同时注明区间两端各代表什么：

- **上界 0.18 元/注**：假设形态能完全控制 p1（`p1: 6 → 3`）。因形态仅解释 p1 方差 1.9%，**该上界不可达**，仅作为"若能做到"的参考天花板；
- **下界 0.005 元/注**：按实测弹性 −0.088 计算，**这才是当前技术条件下最接近真实的数字**。

> **本项能带来约 +0.005~0.18 元/注的期望增益（占成本 0.3%~9%，最可能落在下界附近），不改变中奖概率（恒为 1/17,721,088），远不足以使购彩变为正期望（整体仍约 −50%~−55%）。**

## Q3 AI 的真实岗位

### 3.1 AI 现在实际在做什么（四个明确岗位）

| 环节 | 文件 | 实际产出 | 可验证性 |
|---|---|---|---|
| **① 观察生成** | `engine.py:857-880` → `llm_client.observations_prompt` | 对近期走势的定性观察 JSON | ❌ 无独立验证，仅作为下一轮输入 |
| **② 组合结构优化** | `engine.py:887-899` → `llm_client.tickets_prompt` | 在概率分布 + 硬约束下产出 n 注候选 | ⚠️ **部分**：引擎校验号码合法性（`_parse_tickets_response`，`engine.py:777-790`），但不校验 reasoning 真伪 |

| **④ 规律工坊** | `llm_lab.py:335-430` → `evaluate_claim` | LLM 提规律 → **强制映射维度表 → as-of 回放 → 阶段画像** | ✅ **强验证**（见下） |

**岗位②的提示词已经写得很克制**（`llm_client.py:770-772`，原文）：

> "你是双色球组合结构优化器。双色球为独立随机事件，**不要试图'猜中'号码**，你的职责是在给定概率分布与硬约束下，产出**结构上均衡**、**红球覆盖尽量分散**的候选组合。"

并且 `confidence` 字段被明确限定为"结构置信度，**不代表中奖概率**"。**这说明 AI 的岗位安排其实已经是对的——错的是它头上挂的招牌。**

### 3.2 AI 幻觉进入出号链路的风险：**存在，且只有一个通道**

**🔴 通道：`patterns_used` 无白名单校验。**

```
lottery/engine.py:783  "patterns_used": [str(x) for x in t.get("patterns_used", [])]
web/static/app.js:771  '规律引用：' + escHtml(t.patterns_used.join("、"))
```

LLM 可在 `patterns_used` 里写任意字符串（例如"重号必出规律""和值收敛规律"），后端 `str(x)` 原样透传，前端直接渲染为"规律引用"。**提示词里虽然要求"只能填 tier=usable 的规律"，但那是请求，不是强制。**

用户看到"规律引用：XXX"，会合理推断系统**验证过**它。而当前 `usable=0`——**任何非空的 patterns_used 都必然是幻觉或越权引用。**

**修复（约 10 行）**：下发前用 `patterns_runtime` 的 usable 白名单过滤，`usable=0` 时强制清空并显示"本期无可用规律，本条依据仅为结构均衡"。

**其他通道已封堵（值得肯定）**：
- 号码合法性校验：`len(set(reds))==6` 且范围检查（`engine.py:777-784`）→ 幻觉号码进不来；
- 规律工坊：`evaluate_claim` 把 LLM 的每条 claim **强制映射到 `discovery.FAMILY_BY_KEY` 维度表**，映射不到标 `unmappable`（"不可验证"），再走 `regime_of_filter` 的 as-of 回放 + 阶段 BH 校正（`llm_lab.py:335-415`）→ **这条路径是全系统验证最严的地方，幻觉无法穿过**；
- 置信度偏置：历史上有 LLM +20 恒定偏置导致"25 注里 24 注来自 LLM"，已在 `engine.py:2475-2497` 修平为两族同基准（`LLM_CONF_BIAS`/`OTHER_CONF_BIAS` 默认均 0），注释明确写了"危害是让 LLM 行不行永久不可测"。**这是一次高质量修复。**

### 3.3 用户的期望 vs AI 的岗位：**不匹配，但应该说清而非改岗**

用户说"**用 AI 来预测**"。当前 AI 的四个岗位中：
- 岗位②④**不产出预测**，产出的是"组合结构优化"与"被验证过的规律的归档"；
- 岗位①③本质是"让输出读起来像有推理"。

**我的判断：不应该把 AI 调回"预测"岗——那等于让它去生产必然为假的输出，违反"不能造假"。**

正确做法是**重新命名岗位**（保留动作，改称呼）：

| 现在叫 | 应该叫 | 理由 |
|---|---|---|
| AI 预测号码 | AI **组合结构优化** | 与 `tickets_prompt` 实际做的事一致 |
| AI 找规律 | AI **假设生成器 + 强制回放验证** | 与 `evaluate_claim` 实际做的事一致 |
| AI 规律闭环 → 使用 | AI 规律闭环 → **归档** | 实际产出 0 条可用 |

**即：AI 的岗位安排是对的，招牌是错的。** 这是一个低成本、高收益的修复。

### 方案甲：不推倒，改口径 + 补上唯一真实的数学收益

3. 新增「预算覆盖设计器」：输入预算（如 20 元 = 10 注），按 `min(n,16)/16` 最大化蓝球覆盖，再配对红球；

5. 把 `/api/portfolio/expected-value` 接到前端（目前完全未用）。

**诚实边界**
- 提高的只有**中奖频率**，期望收益恒为负（−50%~−55%）；
- 蓝球覆盖在 n>16 后**完全饱和**，加钱无额外收益；
- 大众度诊断的期望增益仅 0.01–0.10 元/注，且存在非单调性（p1=1 受保底）。

**用户会觉得"有益"吗？**
**部分会。** "同样花 20 元，中个蓝球的概率从 47.6% 提到 62.5%"是一个**用户立刻能懂、且真实**的收益。但它回答不了用户的原始问题"AI 预测"。若只做甲，用户很可能在理解收益后说"所以还是不涨中奖率"。**甲的价值在于止损，不在于翻盘。**

### 方案乙：把产品从"预测器"转为"证据与决策审计器"（推荐）

**交付物**
1. **证据报告**：把已有的 `scan.verdict`、`n_tested=124`、`expected_false_positives=6.2`、多尺度 MDE 表（`index.html:337-347`）、超几何对照图（`index.html:171`）整合为一份**可导出、可引用**的报告：《为什么双色球不可能被预测——基于 3517 期数据的统计审计》。
2. **假设台账**：所有被检验过的维度（124 档 + LLM 工坊提出的 claim）及其**否决理由**公开可查。**"已否决"的清单比"可用"的清单更有价值**——它防止用户被外部"彩票大师"骗。
3. **决策日志**：记录用户每期的选择、理由、事后结果。不做预测，做**行为记录**——这对"我是不是在赌博"这个问题有用。
4. **AI 岗位重命名**（§3.3 表），并把 AI 的实际角色明示在 UI 上："AI 在这里的职责是生成假设并强制验证，不是预测号码。"
5. 修复 `patterns_used` 白名单（§3.2），消除唯一的幻觉通道。

**诚实边界**
- **产品不承诺、也不试图提高中奖率**；
- 最大的风险是**用户不接受这个价值主张**——他想要的是预测，而你给的是"证明预测不可能"；
- 因此必须配一句定位语：**"本系统存在的意义，是让你在花钱之前知道真相。"**

**用户会觉得"有益"吗？**
**取决于用户是谁。** 如果用户已隐约知道彩票不可预测、只是想验证——**乙会觉得极其有用**，因为市面上没有别的东西给他这个证据。如果用户仍坚信 AI 能预测——**乙会让他失望**。

**但为什么还要做？** 因为：
1. **它是唯一不造假的选项**（用户明确要求"不能造假"）；
2. 内核（124 维扫描、BH 校正、e-value、as-of 回放、阶段画像）**已经是全项目最值钱的部分**，推倒重做等于把它扔掉；
3. 它把"找不到"从**失败**重新定义为**结论**——这直接回应用户原话"无法得出任何有益的结果"：**"未检出"本身就是有益的结果，前提是它被可信地证明。**

### 方案丙：推倒重做产品层

**交付物**：保留 `discovery`/`rigor`/`regime`/`evaluate`/`battle` 内核与 `ssq.db`，重写全部前端、路由、术语、价值主张。

**诚实边界**：**重写前端不会让号码变得可预测。** 50 人日之后，核心结论仍是 `usable=0`。

**用户会觉得"有益"吗？**
**不会比乙更多。** 丙只是把乙做得更漂亮。

**为什么还要做？** **我的建议是：现在不做。** 只有当乙验证了"用户确实接受证据型价值"之后，才值得为它投入重做的成本。**在未验证价值主张前推倒重做，是把唯一资产（内核）与最大不确定性（用户接受度）同时押上。**

## 我建议用户决策时可以问的三个问题

**Q-A：你要的"有益"，是"让我更容易中奖"，还是"让我在花钱前知道自己面对什么"？**
如果答案是前者——**必须直说：数学上不可能，任何系统都做不到，继续投入只会得到更精致的幻觉。** 这不是技术问题，是目标问题。
如果答案是后者——方案乙立刻成立，且现有内核已经完成了 80%。

**Q-B：你能接受"系统永远给出 0 条可用规律"作为正常状态吗？**
当前 `usable=0`。如果这是**结论**，系统是成功的；如果这是**故障**，用户会要求工程师去"修好它"——**而唯一的"修法"就是放宽显著性阈值，那就是造假。** 这个决定必须在继续投入前做出来，否则团队会被 KPI 逼向造假。

**Q-C：你愿意先花 8–12 人日做方案甲来验证"用户到底认不认真实收益"吗？**
甲是最便宜的探针：它交付一个用户立刻能懂的真实数字（47.6%→62.5%），**成本低、可回滚、不造假**。如果用户看完这个数字仍说"不是我要的"，那说明问题不在实现、而在价值主张本身——此时应停止投入，而不是加码重做。

## 附：一句话结论

> **这套系统不是一个失败的预测器，而是一个被错误命名为预测器的证据审计工具。**
> 它手里有两个真实的数学收益（蓝球覆盖、分奖摊薄）和一个高质量的"不能预测"证明，却把三者都藏在"智能预测"的招牌后面。
> **继续投入是值得的——但条件是停止卖预测，开始卖真相。**
