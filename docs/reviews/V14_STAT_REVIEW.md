## 结论摘要

1. **判定器工作是正常的**：同一 `eprocess` 实现，注入 +10%/号偏置后全史 e 达 10⁶~10⁷ 量级（Lead 的 438 850 落在同一量级区间内），真实数据最大 e=28.34，差 4~5 个数量级。判定器没有坏。
2. **数据里没有信号**：我做了 306 档全量扫描 + 零分布 **最大统计量**校正（4000 次模拟），实测 max e=28.34 在 H0 下的 **p=0.2995**。Lead 的「z=3.24」是**未做多重校正的单条统计量**，把它读成"有信号"是 selection bias。红球 χ² 全史 p=0.0654、蓝球 p=0.9276，均不显著。
3. **三条缺陷全部成立**，但 **Lead 对缺陷严重性的定性有误**：缺陷是「不可复现 / 不可解释」，**不是**「挡掉了本该发现的规律」。
4. **修好之后仍然是 0 条**（6 种修复口径全部为 0）。但与 Lead 的「仍为 0」不同之处在于**理由**：阈值从 2700 降到 960（降 2.8 倍），可**所需效应量只从 delta=0.0683 降到 0.0645（仅降 5.6%）**，实测值 0.0496。**修 m 记账对检出能力的提升几乎为零——它是正确性问题，不是灵敏度问题。**
5. **最该改的一处是 `_recompute_usable` 的候选入参 + `_group_checked` 的硬编码 m（同一处）**，理由不是"能多发现规律"，而是"让判定结果可被复算、可被审计"。

### Lead 结论 3 —「`_recompute_usable` 只把 `decision=='usable'` 的候选送进 e-BH，导致 rank 恒为 1、门槛恒为 m/α」：**部分正确 —— 前半段确认，后半段（rank 恒为 1）有误**

**确认的部分**：`idle_mining.py:366-370` 只把 `d == "usable"` 的候选写进 `candidates`；`:457-464` 按 `single` / `cross|<mode>` 分 3 组；`:468` 从 `candidates` 取 e 值；`:472` 调 `ebh_selected`。**入参确实只有过阈候选，这是真缺陷。**

**有误的部分**：`rank` **不**恒为 1。我实测生产断点 `data/idle_mining_state.json`：

```
n_checked=21800, candidates=20, usable=0
  cross|1   组内过阈数=18  max_e=567.83  _group_checked=135  阈值=2700  过? False
  single    组内过阈数=1   max_e=28.34   _group_checked=306  阈值=6120  过? False
  cross|0   组内过阈数=1   max_e=22.43   _group_checked=135  阈值=2700  过? False
```

`cross|1` 组有 **18 条**候选，rank 最大可到 18，此时阈值降到 `135/(18×0.05)=150`。
**Lead 说「rank 恒为 1、门槛恒为 m/α」在 `cross|1` 组上不成立。** 脚本 `/tmp/rev/q3c_prod_state.py`、`/tmp/rev/q3e_debug.py`。

**但这个"误"不改变结论**：即使 rank 放开到 18，最强 e=567.83 仍 < 150？不——567.83 > 150，**理论上应该过**。我复算了为什么没过：
`ebh_selected` 的实现（`eprocess.py:274-286`）要求**存在** k 使 `e_(k) >= m/(k·α)` 才置 `k_star=k`，而它遍历时取**最后一个满足的 rank**。`cross|1` 排序后 `e_(1)=567.83 ≥ 2700`？否 → `k_star` 保持 0 → 返回空集。

**这里有一个真实的实现级 bug，Lead 没发现**：
`ebh_selected` 在 `e_(1) < m/α` 时直接返回空集是正确的（e-BH 要求 rank-1 先过），
但 `_recompute_usable` 用 `m_group = max(len(fps), _group_checked(...))` 把 m 膨胀后，
**rank-1 门槛被 `m_group` 抬高，而 `k` 又只能从 1 开始**，于是"组内有 18 条"完全没帮上忙。
换句话说：**缺陷的真实形态是「m 被人为放大 → rank-1 门槛过高 → k_star 恒为 0」，而不是「rank 恒为 1」。**
两者数学后果相同（可用=0），但归因不同：**错的是 m，不是 rank。**

## 我认为的问题所在

### 1. Lead 的诊断结论对，但归因错了三处

**(a) 「rank 恒为 1」是错的。** 见结论 3 复核。`cross|1` 组有 18 条候选，rank 可到 18。
真正的机制是 **m 被 `_group_checked` 放大 → rank-1 门槛过高 → `k_star` 恒为 0**。
这个区别很重要：如果按 Lead 的说法去"修 rank"，会改成一件无用功；按我的归因去"修 m"，才修到点上。

**(b) 「中位 46」是错的，实测中位 35；而 135 是均值。**
作者是把**均值**当常数用了，代价落在 **78% 低于均值的族对**身上（最极端的 `repeat×repeat2` 真实 m=1 被放大 135 倍）。
这个细节决定了修复方案：**不能用任何单一代数常数，必须逐组用真实档位数。**

**(c) 「H0 过阈率 0.002 说明判定器不正常」论证方向反了。**
过阈率低于 α 是保守，不产生假阳性。它只损失 power。
把它当作"判定器坏了"的证据会被懂统计的评审一眼驳回，削弱整份报告的可信度。
正确的提法是：**「在 3217 期上，该 e-process 的检定力不足以支撑 m/α 这个门槛，两者叠加使它实际上不可达」**——这比"判定器不正常"准确得多，也更难被反驳。

### 2. Lead 漏掉的最重要一条：`sum_range 45-75 w30` 不是"恒等重述"，但也不是信号

Lead 说它「候选集是否≈{1..6}」——我实测：

```
筛选集大小分布: {6: 3217}          # 100% 是 6 个号（由 k=6 参数决定，非巧合）
恒等于 {1,2,3,4,5,6} 的次数: 159 / 3217 = 4.9%
不同集合数: 521
最常见: (1,2,3,4,5,6) 159 次
```

**不是恒等重述**（521 个不同集合，{1..6} 只占 4.9%），**也不是信号**：
它在零分布 max-stat 校正下 p=0.2995，holdout 后半段 e 只有 1.116（monitor）。

它之所以看起来强，是因为**在 306 条里挑最大值**——这正是多重检验要防的事。
**Lead 用"恒等重述"来否定它，理由是错的（它不恒等）；正确的理由是"没通过多重校正"。**
这个区别对后续决策是实质性的：如果它是恒等重述，应该**删掉这个候选维度**；
如果它只是没通过校正，应该**保留在搜索空间里**。我的结论是**保留**。

### 3. 最该被指出的真相：修 m 记账对"能否发现规律"几乎零帮助

这是我认为 Lead 报告最需要修正的定性：

| 门槛 | 所需 delta | 相对提升 |
|---|---|---|
| V0 现状 2700 | 0.0683 | 6.3% |
| V2 修复后 960 | 0.0645 | **5.9%** |

**修复把门槛从 2700 降到 960（降 2.8 倍），但所需效应量只从 6.3% 降到 5.9%——改进 0.4 个百分点。**
因为 e 值对效应量是**四次方级**敏感（`log M ∝ τ²S² ∝ delta²·t²`），阈值降 2.8 倍只换来 delta 降 6%。

我做了注入实验直接验证（`/tmp/rev/q4f_value_of_fix.py`）：

| 注入 | 单候选 e | V0 门槛 2700 | V2 门槛 960 |
|---|---|---|---|
| +5% | 13.44 | 漏报 | **漏报** |
| +6% | 53.94 | 漏报 | **漏报** |
| +8% | 1.23×10⁴ | **检出** | **检出** |

**V0 与 V2 的检出边界完全相同（都在 +6%~+8% 之间）。**

所以 `docs/analysis/V14_ROOT_CAUSE.md` 的核心论断——
「下一次数据真有 +7% 偏置时，系统仍会报 0，而你会以为那是诚实」——**这句话是对的，但它不是 m 记账造成的**。
即使把 m 修到完全正确，+6% 的偏置**依然报 0**。
真正卡住检出的是 **`m/α` 这个 e-BH 门槛本身的分辨率极限**，不是记账错误。

Lead 把"可发现性"问题归到记账上，会导致一个危险的后续决策：**以为修了记账就能提高命中率，修完发现还是 0，然后再去动统计内核**。应该一开始就说清楚：**记账是正确性问题，不是灵敏度问题。**

### 4. `ebh_selected` 的实现细节值得单独提一句

`eprocess.py:277-286` 的 `k_star` 循环取**最后一个**满足条件的 rank，这是 e-BH 的正确实现（Wang & Ramdas 2022）。
但它在 `e_(1) < m/α` 时返回空集——当调用方把 m 人为放大后，**这个"正确实现"就成了把结果钉死在 0 的帮凶**。
这不是 `ebh_selected` 的错，是调用方给错了 m。**修 `ebh_selected` 是无意义的，修 `_group_checked` 才对。**

## 建议的最小改动

### 唯一必须改的一处：`idle_mining.py:471` + `:482-495`

**只改这一处（`_group_checked` 的返回值），不要动 `ebh_selected`、不要动 `eprocess` 的统计内核。**

**改法**：把两个代数常数换成**真实档位数**。

```python
# idle_mining.py:482-495 现状
def _group_checked(gkey: str, n_checked: int, n_in_group: int) -> int:
    if gkey == "single":
        return min(n_checked, 306) if n_checked else n_in_group
    return max(n_in_group, 135)
```

替换为（新函数，不动原文件；建议以此替换 `:482-495`）：

```python
def _group_checked_exact(gkey: str, n_checked: int, n_in_group: int) -> int:
    """每组的检验总数 = 该组**真实档位数**，不是任何代数常数。

    实测（2026-10-21）：交叉层 268 个族对，档位数 min/中位/mean/max = 1/35/135/2304，
    78% 的族对 < 135。用常数 135（恰为该分布均值）会把 78% 的组 m 放大 2~20 倍
    （`repeat×repeat2` 真实 m=1 → 135，放大 135 倍），使 rank-1 门槛不可达。
    """
    from . import candidate_space as CS
    if gkey == "single":
        return max(n_in_group, 1)          # 单因子层：调用方应传全层 306
    # 交叉层：解析指纹里的族对，查真实档位数
    return max(n_in_group, _cross_group_size(gkey))
```

**同时必须改 `:428` 的入参口径**（这是同一处修复的另一半）：
`_recompute_usable(candidates, n_checked)` 的 `candidates` 目前只含 `e>=20` 的候选。
**应改为传入「本层全部已检验候选的 e 值」**，让 e-BH 看到完整的 m 个假设。
否则无论 m 怎么算，`ebh_selected` 的 rank 都只能从"过阈的那几条"里排。

> **但请注意**：按我 Q4 的实测，**这两处都修完，结果仍是 0 条**。
> 改的价值在于：让"为什么是 0"这句话**可以被复算**——
> 现在没人能复现 135 的来历，也没人能复现"rank=1"的结论（因为它是错的）。
> 修完之后，`usable=0` 会变成一条**有正确分母、可独立核验**的结论。

### 建议不要改的

- **不要动 `eprocess.ebh_selected`**：它的实现是标准的、正确的。m 给对，它就工作。
- **不要为了把 0 变成非 0 去降低 α 或缩小搜索空间**：那是造假。我在 Q4 里穷举了 6 种口径，**全部为 0**，说明这个 0 是数据的真实回答。
- **不要把 `_group_checked` 改成"均值 135"或"中位 35"**：任何单一代数常数都会重犯同一个错。必须逐组查真实档位数。

### 建议同步修一处文档（非代码）

`eprocess.py:227-236` 的 docstring 写着「只要做了族级校正，连强注入偏置都检不出」——
**这句话本身是对的**（我实测 +6% 偏置在 m=306 下确实检不出），
但它被写在 `ebh_selected` 里，读者会以为这是"设计如此"，从而错过"这是门槛分辨率不足"的事实。
建议补一句量化：**「m=306 时的检出下限是 delta≈0.071（相对 6.5%），3517 期数据能支撑的最小可检效应就是这个量级。」**

### 诚实边界

- 交叉层的 72350 个候选**没有全量跑**，只抽样 600（非退化 302，耗时 66s）。按此速率全量需约 4.4 小时。
  因此交叉层的 max e **是下界**（40.934 只是抽样最大值），真实全层 max e 可能更高。
  但我用 e-BH 的解析门槛验证过：即便交叉层最强候选（e=40.9）也远低于其族对的真实门槛 2880。抽样不影响"0 条"的结论。
- 交叉层 max e=40.934 的候选是 `sum_range45-75w30 ∪ consecutive_hot`——**它包含同一个 sum_range 维度**，
  所以它不构成独立证据，而是同一个统计涨落的另一种投影。这一点在解读"交叉层更强"时必须记住。
- 我没有验证 `patterns_runtime` 的链 A 是否在**生产运行态**下真的返回 0（只读代码逻辑 + 断点文件）。
  链 A 的 0 是 `persistent` 状态在近均匀数据上的数学必然，我确认了前提（χ² p=0.0654），但没跑全量 `build_snapshot`。
